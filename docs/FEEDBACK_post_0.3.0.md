## 001. 도구줄 버튼 단축키 배정 + 툴팁에 단축키 표기

**요청 (원문 요지)**
- 한글 창과 도킹하는 버튼의 단축키를 **Ctrl+D** 로 지정한다.
- 마우스 커서를 올렸을 때 툴팁에 단축키가 함께 떠야 한다.
  - 예: `한글문서와 도킹 (Ctrl + D)`
- 옆에 있는 다른 버튼들도 마찬가지다 — 단축키를 갖고, 툴팁에 병기한다.

**대상 (현재 위 도구줄 구성, `hwp_palette/app.py`)**

| 버튼 | 기호 | 현재 툴팁 | 단축키 |
|------|------|-----------|--------|
| 도킹 | ◫ | 한글과 도킹 (다시 누르면 떼기) / 도킹 떼기 | **Ctrl+D** (확정) |
| 되돌리기 | ↺ | 되돌릴 것이 없습니다 | 미정 |
| 통합 찾기 | ⌕ | 통합 찾기 (Ctrl+K) | Ctrl+K (이미 있음, 표기 방식만 통일) |
| 항상 위 | ⇧ | 항상 위 — 켜짐/꺼짐 | **PageUp** (확정, 002 참고) |
| 설정 | ⚙ | 설정 | 미정 |
| 도움말 | ? | 도움말 | 미정 |

**작업 시 확인할 것**
- 표기 형식 통일 — `⌕` 는 `통합 찾기  (Ctrl+K)`, 요청 예시는 `(Ctrl + D)` 로 공백이 다르다. 하나로 정한다.
- 도킹 버튼은 상태에 따라 툴팁이 바뀐다(`_show_dock_buttons`) — 켜짐/꺼짐 두 문구 모두에 단축키를 붙여야 한다.
- 항상 위(⇧)도 `_toggle_top` 에서 툴팁을 갈아끼우므로 같은 처리 필요.
- 도킹 중에는 한글 창이 앞에 있으므로, Ctrl+D 가 한글 쪽으로 먹히지 않는지 확인해야 한다(전역 단축키로 잡을지 창 단축키로 잡을지 결정 필요).

**미정 / 물어볼 것**
- ↺ · ⚙ · ? 의 단축키를 무엇으로 할지. (⇧ 는 002 에서 확정)

## 002. 항상 위(⇧) 단축키 = PageUp

**요청**
- 항상 위 기능의 단축키를 **PageUp** 으로 한다.

**작업 시 확인할 것**
- 툴팁 병기는 001 규칙을 따른다 — `항상 위 — 켜짐 (PageUp)` / `항상 위 — 꺼짐 (PageUp)` 두 문구 모두.
- PageUp 은 조합키가 아니라 단독키라, 목록·스크롤 영역에 포커스가 있을 때 스크롤 동작과 부딪힐 수 있다. 어느 위젯에 포커스가 있어도 항상 위 토글이 먼저 먹게 할지, 입력칸(검색·필터)에서는 비켜줄지 정해야 한다.
- 도킹 중에는 한글 창이 앞이므로 001 과 같은 문제(창 단축키 vs 전역 단축키)가 그대로 걸린다.

## 003. 되돌리기(↺) 단축키를 Ctrl+Z 로 하면? — 검토 결과

**결론: 권하지 않는다.** 다른 키를 쓰거나, 쓰더라도 "메인 창에 포커스가 있을 때만" 으로 좁혀야 한다.

### 문제 1 — Ctrl+Z 는 이미 다른 되돌리기가 쓰고 있다 (가장 큰 문제)

환경설정(팔레트 편집) 창이 `hwp_palette/ui/palette_ui.py:659` 에서 `bind_all("<Control-z>")` 로 **블럭 배치 되돌리기**를 잡고 있다.
- `bind_all` 은 Tk 의 "all" 태그라 **앱 전체**에 걸린다. 메인 창에서 같은 키를 또 `bind_all` 하면 나중 것이 앞 것을 덮어써 하나만 남는다.
- 이 사고는 이미 한 번 겪었다 — `palette_ui.py:654` 주석("각자 bind_all 하면 Tk 의 'all' 태그를 서로 덮어써 나중 것만 남는다").
- 온보딩 안내에도 "환경설정에서 Ctrl+Z" 로 이미 적혀 있다 (`ui/onboarding.py:39`).

### 문제 2 — 같은 키에 되돌리기가 세 가지가 된다

| 무엇을 되돌리나 | 지금 입구 |
|------------------|-----------|
| 팔레트 블럭 배치 | 환경설정 창의 Ctrl+Z |
| 한글 **문서** 내용 (변환·삽입 묶음) | 도구줄 ↺ |
| 한글 자체의 되돌리기 (1단계씩) | 한글 창에서 Ctrl+Z |

Ctrl+Z 하나에 이 셋이 얹히면, 사용자는 **지금 어느 창이 앞이냐**에 따라 결과가 달라지는 키를 갖게 된다. 예측이 안 된다.

### 문제 3 — 오발의 대가가 크다

↺ 는 한글 문서를 실제로 되돌린다 — 변환 한 번이 여러 동작으로 쪼개져 있어 **Ctrl+Z 를 여러 번 대신 보내는** 구조다 (`hwp/hwp_engine.py:617` 주석). Ctrl+Z 는 손에 붙은 키라 습관적으로 눌리는데, 한 번 잘못 누르면 문서가 여러 단계 날아간다. 다른 버튼(도킹·항상 위)의 오발은 되돌리기 쉽지만 이건 아니다.

### 문제 4 — 도킹 중에는 어차피 한글이 가져간다

도킹 중에는 한글 창이 앞이므로 우리 `bind_all` 은 안 먹고 한글 자체의 Ctrl+Z 가 먹는다. 같은 키인데 상황에 따라 "1단계 되돌리기"와 "묶음 되돌리기"로 갈린다. 전역 단축키로 가로채면 **한글의 평범한 Ctrl+Z 를 빼앗는 것**이라 더 나쁘다.

### 문제 5 — 입력칸 안에서

이름 편집·검색 등 텍스트 위젯 안에서 Ctrl+Z 는 "글자 되돌리기"로 기대된다. 여기서 문서 되돌리기가 튀면 놀란다.

### 대안

1. **Ctrl+Alt+Z** — 변환이 `Ctrl+Alt+T` 인 것과 짝이 맞는다. "변환한 것을 되돌린다"는 뜻이 그대로 읽히고, 한글의 Ctrl+Z 를 뺏지 않는다. **가장 권함.**
2. **Ctrl+Shift+Z** — 흔히 '다시 실행'으로 쓰이는 자리라 헷갈릴 수 있다. 차선.
3. **Ctrl+Z 를 쓰되 메인 창 한정** — `bind_all` 대신 메인 창에만 `bind` 하고, 환경설정 창이 떠 있을 때는 그쪽이 갖게 한다. 문제 1·5 는 풀리지만 문제 2·3 은 남는다.

**결정 대기: 위 1·2·3 중 무엇으로 할지.**

## 004. 설정(⚙) 단축키 — 다른 프로그램은 어떻게 하나

**결론: `Ctrl+,` (컨트롤 + 쉼표) 가 사실상 표준이다.**

### 근거

- **VS Code** — `Ctrl+,` (Windows/Linux), `Cmd+,` (macOS) 로 설정 편집기를 연다. 공식 문서에 기본 키로 실려 있다.
- 같은 키를 쓰는 프로그램들 (개발 도구 밖까지 퍼진 관례): Visual Studio, Slack, Discord, Notion, Figma, Spotify, Chrome 계열 확장 등.
- 뿌리는 **macOS 관례**다. Apple 이 오래전부터 '환경설정 = Cmd+,' 로 못박았고, 크로스플랫폼 앱들이 Windows 로 옮기면서 Ctrl+, 로 그대로 가져왔다.

### 다른 방식들 (참고, 우리에겐 안 맞음)

- **Windows 자체 설정** = `Win+I`. OS 전용이라 프로그램이 쓸 수 없다.
- **옛 Windows 데스크톱 앱** (Office 등) = 단독 단축키 없이 `Alt` → 메뉴 문자 순서로 들어간다 (예: 도구 → 옵션). 우리는 메뉴 표시줄이 없어 해당 없음.
- **F10 / Alt+F10** — 일부 앱이 옵션 창에 쓰지만 관례라 할 만큼 퍼지지 않았다.
- **Chrome** — 설정에 단축키가 아예 없다 (`Alt+E` → S). 참고할 것 없음.

### 우리 프로그램에 적용할 때

- `Ctrl+,` 는 지금 코드 어디에도 잡혀 있지 않다 (`Control-comma` 검색 결과 없음). **충돌 없음.**
- 한글도 Ctrl+, 를 쓰지 않는다(한글의 환경설정은 메뉴/도구 쪽). 도킹 중 문제 낮음.
- Tk 표기는 `<Control-comma>` 다.
- 툴팁: `설정 (Ctrl+,)` — 001 의 표기 형식 결정에 따른다.

**출처**
- https://code.visualstudio.com/docs/configure/keybindings
- https://code.visualstudio.com/docs/reference/default-keybindings
- https://support.microsoft.com/en-us/windows/keyboard-shortcuts-in-windows-dcc61a57-8ff0-cffe-9796-cb9706c75eec (Win+I = Windows 설정)

## 005. 통합 찾기(⌕) 를 Ctrl+F 로 — 충돌 검토

**결론: 충돌 없다. 권한다.** 다만 지금 있는 `Ctrl+K` 를 어떻게 할지만 정하면 된다.

### 충돌 점검

| 살펴본 것 | 결과 |
|-----------|------|
| 우리 코드에 `Control-f` 바인딩 | **없음** (`Control-f`/`Control-F` 검색 결과 0건) |
| 이미 잡힌 우리 단축키 | Ctrl+T(변환) · Ctrl+K(찾기) · Ctrl+1~9(블럭) · Ctrl+Z/Y(환경설정 창) · Ctrl+Alt+T(전역 변환) — Ctrl+F 와 겹치는 것 없음 |
| 한글의 Ctrl+F | 한글도 '찾기'다. **뜻이 같아서** 사용자가 헷갈릴 일이 없다 — 게다가 우리 바인딩은 `bind_all` 이라 **우리 창이 앞일 때만** 먹는다. 한글에서 누르면 한글 찾기가 뜬다. 서로 안 뺏는다 |
| 전역으로 잡으면? | **잡으면 안 된다.** Ctrl+F 를 전역으로 가로채면 한글·브라우저·탐색기의 찾기를 전부 빼앗는다. 지금 전역인 것은 Ctrl+Alt+T 하나뿐이고, 그 이유가 `app.py:2525` 주석에 적혀 있다 (다른 프로그램 것을 뺏지 않기 위해 Alt 를 끼움) — 같은 원칙을 지킨다 |
| 입력칸 안에서 | Entry/Text 위젯의 Tk 기본에 Ctrl+F 는 "커서 한 칸 오른쪽"(emacs 식) 이 걸려 있다. 검색·이름 입력 중 Ctrl+F 를 누르면 찾기 창이 뜨게 되는데, 실사용에서 문제될 확률은 낮다. 다만 **찾기 창이 이미 떠 있을 때 그 안에서** Ctrl+F 를 누르는 경우는 확인 필요 (`_open_search` 는 이미 떠 있으면 앞으로 가져오게 돼 있음 — `app.py:2423`) |

### Ctrl+K 를 어떻게 할지 (결정 필요)

1. **둘 다 둔다** — Ctrl+F 를 추가하고 Ctrl+K 도 남긴다. 안전하지만 도움말·툴팁에 뭘 적을지 정해야 한다(툴팁엔 Ctrl+F 만 적고 Ctrl+K 는 도움말에만 남기는 식). **권함.**
2. **Ctrl+F 로 갈아탄다** — Ctrl+K 를 없앤다. 깔끔하지만 이미 손에 익은 사용자에겐 갑작스럽다. 도움말 3곳(`ui/help_content.py:134`, `ui/onboarding.py:35`, `app.py:1519`)과 툴팁을 모두 고쳐야 한다.

**어느 쪽이든 고쳐야 할 곳**: `app.py:1367`(툴팁), `app.py:2520`(바인딩), `app.py:1519`(도움말 요약), `ui/help_content.py:134`, `ui/onboarding.py:35`.

**~~결정 대기~~ → 결정됨: 2 (갈아타기). Ctrl+K 는 남기지 않는다.** (006 참고)

## 006. 단축키 확정분

**Ctrl+K 폐기 시 지울 곳**: `app.py:2520-2521`(바인딩), `app.py:1367`(툴팁), `app.py:1519`(도움말 요약), `ui/help_content.py:134`, `ui/onboarding.py:35`.

**설정 = Ctrl + `+` 에 대해 확인해야 할 것 (작업 전 확인, 지금은 기록만)**
- 한국어 자판에서 `+` 는 `Shift` 를 눌러야 나오는 글쇠다(`=` 와 같은 자리). 그래서 실제 키 조합은 **Ctrl+Shift+=** 가 된다. Tk 로는 `<Control-plus>` 가 아니라 `<Control-Shift-equal>` 또는 `<Control-KeyPress-plus>` 로 잡아야 먹을 수 있다 — 구현 시 실기 확인 필요.
- 숫자 자판(키패드)의 `+` 는 **다른 글쇠**다(`<Control-KP_Add>`). 둘 다 잡을지 정해야 한다.
- `Ctrl` + `+` 는 많은 프로그램에서 **화면 확대**로 쓰인다(브라우저·한글 포함). 우리 창 안에서만 먹으므로 남의 것을 뺏지는 않지만, 우리 창에 '크게' 모드가 있어 사용자가 확대로 착각할 소지가 있다. (004 조사에서는 `Ctrl+,` 가 표준이었으나 **사용자 결정은 `Ctrl + +`** 이다.)
- 툴팁 표기: `설정 (Ctrl + +)` — 001 의 표기 형식 결정에 따른다.

## 008. 물감 창고 ↔ 물감 미리보기 사이에 위계가 없다

**요청**
- 지금 두 판이 붙어 있어 하나처럼 보인다. **팔레트 설정 ↔ 물감 창고 사이처럼 떨어진 느낌**의 위계가 있어야 한다.
- 다만 미리보기가 **지금처럼 넓을 필요는 없다.**

**메모**
- 지금 팔레트 설정과 창고 사이에는 `〉` 접기 손잡이가 있어 그것이 경계 역할을 겸하고 있다. 미리보기 쪽은 그 장치가 없어 경계가 흐리다.
- 접기 기능을 안 넣기로 했으므로, 경계는 **여백 + 구분선**으로 만든다. 007(폭 고정)과 같이 작업해야 한다 — 폭 배분을 한 번에 정해야 두 번 안 만진다.

## 011. [버그] '도구' 를 고르면 창이 깨지고 무슨 도구가 있는지 알 수 없다

**증상**
- 빈칸 → '도구' 를 누르면, 제목 자리에 `{'key': 'set_format', 'name': '기본 서식', 'hint': …}` 같은 **날 데이터**가 그대로 찍히고 창이 가로로 화면 끝까지 늘어난다.
- 목록에는 실제 도구가 아니라 **방금 본 5종(특수기호·템플릿·서식 조합·양식·도구)이 또** 나온다. 어떤 도구를 쓸 수 있는지 알 수 없다.

**원인 (확정)**

`hwp_palette/ui/palette_ui.py` 안에 **`_ToolPickDialog` 라는 이름의 클래스가 두 개** 있다.

| 줄 | 무엇 | 생성자 |
|----|------|--------|
| `palette_ui.py:2843` | 진짜 '도구 고르기' 창 (이름+설명 두 줄) | `(master, actions)` |
| `palette_ui.py:3137` | '무엇을 넣을까' 종류 고르는 창 | `(master, span, rows=1)` |

파이썬은 **나중 정의가 앞 정의를 덮어쓴다.** 3137 이 뒤에 있으므로 이름 `_ToolPickDialog` 는 3137 을 가리킨다.

그래서 `_add_builtin` (`palette_ui.py:2642`) 이

```python
pick = _ToolPickDialog(self, builtin_actions.BUILTIN_ACTIONS)
```

를 부르면 2843 이 아니라 **3137 이 불린다.** 도구 목록(dict 의 리스트)이 `span` 자리로 들어가고, 3137 은 그것을 `f"{span}칸"` 으로 글자화해 제목 라벨에 그린다 (`palette_ui.py:3156-3158`).
→ **날 데이터가 제목에 찍히고, 그 긴 한 줄이 창 폭을 끌고 늘어난다.** 목록이 5종으로 나오는 것도 3137 의 `_TOOLS` 이기 때문이다.

즉 **2843 의 제대로 만든 창은 한 번도 안 불리는 죽은 코드**다. 2843 주석에 "2026-07-31" 이라 적혀 있으니, 오늘 새로 만들면서 이름이 겹친 것이다.

**고칠 방향 (지금은 기록만)**
- 둘 중 하나의 이름을 바꾼다. 2843 → `_BuiltinPickDialog`, 3137 → `_BlockKindDialog` 처럼 **무엇을 고르는 창인지**가 이름에 드러나게.
- 이름만 바꿔도 증상은 사라진다. 다만 `_add_builtin` 이 부르는 쪽도 같이 고쳐야 한다.
- 같은 파일에 이름이 겹친 다른 클래스는 **없다** (확인함 — `palette_ui.py` 의 중복 클래스명은 `_ToolPickDialog` 하나뿐).
- 009/010(창고 개편)에서 이 창들을 재사용할 계획이므로, **이름 정리를 먼저 하고 개편에 들어가는 것이 순서**다.

## 012. 서식 조합 블럭 — 수치 칸이 전부 비어 있다

**요청**
- '서식 조합 블럭 만들기' 창의 수치 입력칸이 모두 빈칸이다. **대략적으로나마 수치가 들어 있어야** 한다.
- 모든 값을 사용자가 다 정해야 하면 입력하기 골치 아프다.

**대상 칸 (사진 기준)**

| 항목 | 단위 | 기본값 후보 (제안 — 확정 필요) |
|------|------|-------------------------------|
| 글씨 크기 | pt | 10 (한글 기본) |
| 자간 | — | -5 |
| 줄간격 | % | 160 |
| 들여쓰기 | pt | 10 |
| 내어쓰기 | pt | 10 |
| 왼쪽여백 | mm | 5 |
| 오른쪽여백 | mm | 5 |
| 자간 자동조절 | % | 20 (설명에 "0~50 권장" 이라 적혀 있음) |

**설계 시 정할 것**
- **빈칸 vs 회색 예시글자(placeholder)** — 진짜 값을 넣어두면 체크만 하고 지나쳐도 그 값이 적용된다. 회색 예시글자는 안내는 되지만 체크하면 여전히 빈칸이라 오류가 난다. **진짜 값을 넣어두는 쪽**을 권한다(요청 취지가 "골치 아프다" 이므로).
- 체크를 안 한 항목의 값은 저장되지 않아야 한다 — 기본값이 들어 있어도 체크 안 하면 무시.
- 위 후보 수치가 실제로 쓸 만한지는 사용자 확인 필요. 특히 자간·줄간격은 문서 성격을 탄다.
- 창이 세로로 길다(17줄). 기본값이 채워지면 "체크 → 저장" 만으로 끝나므로 체감은 훨씬 나아진다. 다만 항목 묶음(글자 / 문단 / 여백)으로 나누는 것도 같이 볼 만하다 — 별건으로 둘지 결정 필요.

## 013. [질문] 한글에 '내용 말고 서식만 복사' 기능이 있나

**답: 있다. 한글의 '모양 복사' 기능이다 (단축키 `Alt+C`).**

- 서식을 가져올 글자·문단에 커서를 두고 `Alt+C` → 무엇을 복사할지 묻는 창이 뜬다 (글자 모양만 / 문단 모양만 / 글자+문단 / 셀 모양 등).
- 그 뒤 적용할 부분을 선택하고 다시 `Alt+C` 를 누르면 **내용은 그대로 두고 모양만** 입혀진다.
- 표 안에서는 셀 테두리·배경까지 복사할 수 있다.

**우리 프로그램에 쓸 수 있는 방향 (아직 결정한 것 없음)**

이게 012(서식 조합 블럭 기본값)와 바로 이어진다. 지금은 사용자가 수치를 **손으로 다 적어야** 서식 조합 블럭이 만들어지는데, 다음처럼 바꿀 수 있다.

1. **"지금 커서 자리의 서식 읽어오기" 단추를 서식 조합 창에 붙인다.**
   한글에서 마음에 드는 부분에 커서를 두고 이 단추를 누르면, 글꼴·크기·자간·줄간격·여백 칸이 **그 값으로 자동으로 채워진다.** 그 뒤 필요 없는 항목의 체크만 끄면 된다.
   → 012 의 "기본값" 문제를 근본에서 없앤다. 남이 정한 기본값보다 **내 문서에서 뽑은 값**이 훨씬 쓸모 있다.
2. **모양 복사 자체를 도구 블럭으로 둔다** — 팔레트 버튼 하나로 '모양 복사 뜨기 / 입히기'.

**기술 메모**
- 우리는 이미 `hwp/exam_engine.py` 에서 `ParagraphShape`·`HParaShape` 로 문단 서식을 **쓰고** 있다. 같은 API 를 `GetDefault` 로 **읽어오는** 것도 되므로, 위 1안은 새 기술이 필요하지 않다.
- 다만 '선택 영역이 없을 때 커서 자리 서식을 읽는' 동작은 실측이 필요하다 — 빈 문단·표 안·글상자에서 값이 어떻게 나오는지.

## 014. '문항 엑셀' 창 — 어떻게 쓰라는 건지 가늠이 안 잡힌다

**요청**
- 창을 열어도 이 기능을 어떻게 써야 하는지 알 수 없다.

**왜 안 읽히는지 (진단)**

1. **일이 창 밖으로 나갔다 와야 끝난다.** 실제 순서는
   `① 엑셀 양식 만들기 → (창을 떠나) 엑셀에서 채우기 → ② 엑셀 파일 고르기 → 마크다운 복사 → (창을 떠나) 한글에 붙여넣기 → 선택 → 마크다운 변환`
   여섯 단계 중 **셋이 이 창 밖**이다. 그런데 창은 ①②만 번호를 붙여 놓아, 나머지가 어디서 벌어지는지 안 보인다.
2. **창을 처음 열었을 때 쓸 수 있는 것은 사실상 단추 하나**(엑셀 양식 만들기)뿐인데, 화면의 **절반 이상이 아직 못 쓰는 빈 상자 두 개**다. 눈이 가는 곳과 눌러야 할 곳이 다르다.
3. **'양식' 이라는 말이 두 뜻으로 쓰인다.** 여기의 '양식'은 **엑셀 파일**이고, 이 프로그램의 물감 분류 '양식'은 **hwp 파일**이다. 같은 창을 쓰는 사람에게 두 뜻이 겹친다.
4. **'조각' 이 설명 없이 나온다** — "등록된 조각이 있는 것만 보입니다", "등록해 둔 조각 서식 그대로". 조각을 어디서 등록하는지 이 창에는 없다. 드롭다운에 왜 어떤 것은 있고 어떤 것은 없는지 알 수 없다.
5. **안내가 두 군데로 갈라져 있다.** 위의 '이 창에서 할 수 있는 것' 상자는 네 줄을 한꺼번에 쏟아붓고, 정작 "지금 무엇을 할 차례인지"는 창 **맨 아래 구석**의 작은 줄(`① 양식을 만들어 엑셀에서 채워 오세요`)에만 있다. 가장 중요한 문장이 가장 안 보이는 자리에 있다.
6. **단추가 네 개 흩어져 있다** (엑셀 양식 만들기 / 엑셀 파일 고르기 / 정답표 복사 / 마크다운 복사). 어느 것이 먼저인지 자리로는 안 읽힌다.

**고칠 방향 (제안 — 확정 필요)**
- **단계 화면으로 바꾼다.** 한 번에 한 단계만 보이게 하고, 지금 할 일 하나만 크게 띄운다. 창 밖에서 하는 일(엑셀에서 채우기 / 한글에 붙여넣기)도 **정식 단계로 넣는다** — "이제 엑셀이 열렸습니다. 채운 뒤 돌아와 [다음]을 누르세요".
- 위의 '이 창에서 할 수 있는 것' 상자는 없앤다 — 단계마다 필요한 한 줄만 그 자리에서 말한다.
- '양식' → **'엑셀 서식 파일'** 처럼 겹치지 않는 말로 바꾼다.
- '조각' 이 무엇이고 어디서 등록하는지 한 줄 안내 + 등록 화면으로 가는 입구를 붙인다.
- 첫 화면에서 '예시 문항 5개 넣기' 를 **기본 켬**으로 둔다 — 빈 엑셀보다 채워진 예시가 훨씬 빨리 이해된다.

**메모**: 이건 문구 손질로 끝날 일이 아니라 **창 구조를 다시 짜는 일**이다. 009/010(창고 개편)과 별개 덩어리로 잡는 게 좋다.

### 2026-07-31 논의 2차 — 걸음 수 자체를 줄이기

단계 화면으로 다듬는 것과 별개로, **여섯 걸음 중 마지막 넷을 하나로 접을 수 있다**:
지금은 `마크다운 복사 → 한글에 붙여넣기 → 선택 → 마크다운 변환` 을 사용자가 손으로 하는데,

## 017. [새 개념] 물감 섞기 — 요소를 조합해 이름 붙인 꾸러미

**사용자 기획 (원문 요지)**
- 시험문제를 뜯어보면 다양한 것들이 **반복**된다. 요소가 1~5 있다면 문항마다 조합이 다르다: 1234 / 1235 / 1245 / 12345 …
- 요소 하나하나를 매번 마크다운으로 변환하는 게 아니라, **조합에 이름을 새로 지정**한다: 12345 = 한 묶음(가), 1234 = (나), 1245 = (다).
- 그러면 시험지 입력은 `나 / 1235 / 다 / 가 / 가` 처럼 **꾸러미 이름의 나열**이 된다. 이런 꾸러미를 만들어내고 싶다 — 이름은 **물감 섞기**.
- 엑셀 기능은 이것들을 지정해 내보내고, **바로 옆 셀에 마크다운 형태로 알아서 출력**되기를 희망. 목적은 시험문제 출제·관리의 편리함.
- "엑셀 안에 들어가면 내가 골라놓은 물감 혹은 섞인 물감을 골라서 마크다운으로 입력할 수 있어야" — 정리가 안 되어 언어화 요청.

**Claude 정리 — 세 층 구조**

| 층 | 무엇 | 예 |
|----|------|----|
| ① 요소 (물감) | 문항을 이루는 낱개 조각 — 각 빈칸에 이름표 | 번호·지문 박스·사진 자리·발문·보기 박스·선지 5개 |
| ② 꾸러미 (섞은 물감) | 요소들의 **순서 있는 조합**에 이름 | 가 = ①②③④⑤ / 나 = ①②③④ / 다 = ①②④⑤ |
| ③ 문항 (내용) | 꾸러미 하나 + 채워 넣을 내용 | "3번 문항은 '가' 꾸러미에 이 지문·이 선지" |

**결정적 근거 — 창고가 이미 증거다.** 지금 템플릿 24개의 이름들(합답형**1사진3선지**, 합답형**2사진3선지**, 학교합답**2사진5선지**…)이 전부 **조합 코드**다. 조합이 하나 늘 때마다 hwp 조각을 통째로 새로 만들어 온 것 — 물감 섞기는 요소와 조합을 분리해서 이 폭발을 없앤다. 요소 몇 개 + 꾸러미 이름들이면 24개가 필요 없다.

**엑셀의 새 그림 (이 위에서 014 재설계)**
- 내보낸 엑셀의 행마다: **[꾸러미 드롭다운(가/나/다…)] + 내용 칸들 + 옆 셀에 마크다운 자동 조립**.
- "골라서 마크다운으로 입력"의 정체 = 행마다 드롭다운으로 꾸러미를 고르면, 내용을 채우는 순간 옆 셀에 완성 마크다운이 나타나는 것.
- 기술: openpyxl 로 데이터 유효성 검사(드롭다운)와 수식(IF·TEXTJOIN·CHAR(10)) 을 **엑셀 파일에 미리 심어서** 내보낼 수 있다 — 실측 필요하지만 표준 기능.
- 마크다운 조립을 엑셀 수식으로 할지, 불러올 때 프로그램이 할지(현행)는 결정 필요 — 수식이면 엑셀만으로 완결, 프로그램 조립이면 검증(잘못 쓴 칸 짚기)이 쉬움. 둘 다도 가능.

**전제**: 빈칸 이름표(014 논의)가 이 전부의 바닥이다 — 요소의 빈칸에 이름이 있어야 꾸러미의 열이 나온다.

**상태**: 개념 정리. 확인 대기 — ① 요소의 뜻이 위 표 ①이 맞는지 ② 섞기 입구(창고에서 요소 여러 개 골라 [섞기]?) ③ 마크다운 조립 위치(엑셀 수식 vs 불러올 때 vs 둘 다).

> **✅ 2026-07-31 사용자 정의 확정** — "겹치기는 하나의 위계를 설정하는 것, **섞기는 여러 물감을 섞어서 하나의 물감을 만드는 것**." 두 개념은 완전히 다르다. 겹치기(018)는 논의 완료, 섞기는 아래에서 상세 설계 논의 중.

## 018. [새 기능] 물감 겹치기 — 팔레트 한 칸에 여러 물감

**요청 (원문 요지)**
- 선지 스타일이 5개면 버튼 5개는 **공간 낭비가 심각**하다.
- 애플처럼 **블럭을 잡고 겹치면** "물감을 겹치겠습니까?" 알람 → 알겠다고 하면 **겹친 물감의 전체 이름**을 정한다.
- 팔레트에서 그 물감을 누르면 **세부적으로 어떤 것을 쓸지 고르게** 한다. 시안 요청.

**설계 (시안 G 절)**
- **만들기**: 환경설정에서 블럭을 다른 블럭 위로 끌면 받는 칸이 겹침 표시로 바뀜 → 놓으면 확인창("물감을 겹치겠습니까?") + 이름 입력 → 한 칸이 됨.
- **쓰기**: 팔레트에서 겹친 칸(이름 + 개수 배지 + 겹친 종이 모양)을 누르면 **팝오버**로 안의 물감 목록 → 하나 누르면 실행. 특수기호가 쓰는 팝오버 방식 재사용(확정 결정과 일치).
- **편집**: 환경설정에서 겹친 칸을 열어 빼기/추가/순서/이름. 밖으로 끌면 낱개 복귀.
- **원칙**: 겹침은 **배치**다 — 창고에는 낱개 그대로 (009 "창고가 진짜 분류, 팔레트는 배치" 원칙 그대로).

## 015. [새 기능 제안] 문서 해체 — 문서 하나로 팔레트 만들기

**요청 (원문 요지)**
- 복잡한 문서가 있을 때 그걸 하나 집어넣으면, **글자 덩어리(문단 단위)·표 단위를 하나하나 보여주면서** 등록할지 말지를 정하고, 태깅하고, 저장하는 기능.
- 즉 **하나의 양식 틀(팔레트 자체)을 통째로 만들어 버리는** 기능. 도킹이 거의 된 상황이라 불가능하지 않을 것 같다 — 어떻게 구현하면 편리할지 아이디어 요청.

**설계 아이디어 (시안 E 절에 그림)**

흐름: 문서 열기(도킹) → [문서 해체] 훑기 → 요약("서식 6벌 · 표 3개") → 하나씩 확인(등록/건너뛰기/이름·태그) → 팔레트 탭 자동 생성.

짧게 끝나게 만드는 열쇠 넷:
1. **같은 서식 묶기** — 문단이 200개여도 (글자 모양 + 문단 모양)이 같은 것을 묶으면 서식은 보통 몇 벌. 확인할 것이 문서 길이와 무관해진다. 쓰인 횟수("141개 문단에서 쓰임")를 붙이면 가장 많이 쓰인 것 = 본문체라 이름 짓기도 쉽다.
2. **실물 하이라이트** — 조각마다 미리보기를 그리지 않고, 도킹된 한글 창에서 그 조각을 **선택**해 보여준다. 도킹이 미리보기를 겸한다.
3. **자동 이름** — 표는 "표 5×3", 서식은 "12pt 굵게 · 줄간격 180%" 식으로 미리 채운다.
4. **팔레트 자동 생성** — 마치면 "등록한 N개로 새 팔레트 탭을 만들까요?" 배치는 등록 순서, 재배치는 환경설정에서 평소처럼.

조작: Enter=등록, Space=건너뛰기 — 손 안 떼고 진행.

**실기 확인 필요**
- 문단 서식 읽기(013/D 와 같은 확인 — 빈 문단·표 안·글상자에서 값이 어떻게 나오는지)

- 긴 문서 훑기 속도
- 표 안·글상자 안까지 훑을지 범위

**상태**: 아이디어 정리 완료, 채택·이름·범위 결정 대기.

## 016. [새 기능 제안] 자간 자동 보정 — 단어가 줄 끝에서 잘리지 않게

**요청 (원문 로직)**
- 가장 위 두 줄을 본다 → 첫 줄의 자간을 **늘릴지 줄일지** 판단 → 수정 → 두 번째 줄을 본다 → … **한 줄씩 반복.**
- 자간 때문에 불필요한 줄바꿈이 일어나거나 단어가 잘리는 것을 방지하는 시스템.

**전제 정리 (가정 — 다르면 정정 요청)**
- 한글에는 이미 **어절 단위 줄바꿈**(단어가 안 잘리게)과 **자간 자동 좁힘(0~50%)** 이 있고, 우리 서식 창에도 둘 다 체크박스로 있다(012 사진).
- 어절 단위를 켜면 단어는 안 잘리지만 줄 끝이 헐렁해지는 문제가 남는다. 요청은 **"단어는 안 잘리면서 줄도 헐렁하지 않게", 줄 단위로 자간을 미세 조정**하는 것으로 이해했다.

**기술 검토 (1차)**
- 줄 단위 선택: 한글 API 에 줄 시작/끝 이동이 있어 시각적 한 줄을 선택하는 것은 가능해 보인다 — 실측 필요.
- 판단 기준이 핵심 난제: "이 줄 끝에서 단어가 잘렸는가 / 다음 줄 첫 어절이 당겨 올라올 수 있는가"를 API 로 알아내야 한다 (줄 끝 위치·다음 어절 폭 측정).
- **사용자가 제시한 '위에서 아래로 한 줄씩' 순서가 정확히 옳다** — 첫 줄 자간을 바꾸면 아래 전체가 다시 흐르므로, 확정된 줄부터 차례로 내려가야 재흐름 파급을 피한다.
- 위험 요소:
  1. 늘림/줄임 진동(무한 루프) — 자간 범위 상한(예: −8% ~ +4%)과 줄당 시도 횟수 제한 필요
  2. 한 줄 안에 서식이 여러 벌이면 자간 적용이 조각남
  3. 양쪽 정렬(어절 간격 늘림)과의 상호작용
  4. 동작이 수십 번 쌓임 — **↺(되돌리기 묶음 세기)에 반드시 편입**
- 적용 범위는 문서 전체가 아니라 **선택 영역(없으면 커서 문단)** 부터 시작할 것을 권함.

**상태**: 아이디어 접수 + 1차 기술 검토. 실측(줄 선택·줄 끝 판정) 후 채택 결정.

| | 방식 A — 어절단위 켜고 좁힘만 | 방식 B — 어절단위 끄고 양방향 (사용자 로직 그대로) |
|--|--|--|

## 019. 우클릭 메뉴가 엉뚱한 곳에 뜬다

**원인** — 메뉴(Popover)를 **타일 위젯을 앵커로** 펼쳤다. 그런데 메뉴를 열기
직전 `_set_selection` 이 타일을 다시 칠하는 중이라, 그 순간 위젯의 화면 좌표가
창 밖 값으로 잡혔다. 좌표 계산 자체는 정상이었다(실측: 앵커가 멀쩡하면
`217x66+348+199` 로 정확히 붙는다) — 잘못된 것은 **무엇을 기준으로 삼았는가**다.

**고침** — `Popover.show_at(x, y)` 를 만들어 **커서 자리**에 편다. 위젯 기하에
아예 기대지 않으므로 같은 사고가 다시 날 수 없고, 맥락 메뉴가 누른 자리에 뜨는
것은 운영체제 관례이기도 하다. 팔레트 블럭·창고 물감·하위 분류 탭 세 곳 모두 적용.

## 020. 선택하지 않은 물감의 미리보기가 남는다

**원인** — 도구 카드를 고르면 `_select` 가 **미리보기 판을 아예 건드리지
않았다**(도구는 라이브러리 항목이 아니라 그렸다). 그래서 직전에 고른 템플릿의
그림이 그대로 남아 지금 고른 것의 내용처럼 보였다.

**고침** — ① 도구도 판에 보낸다(아래 023 의 도구 판). ② 고른 것이 없으면
(격자 블럭을 고르면) 판을 **빈 상태**로 만든다 — "미리 볼 내용이 없으면 미리보기가
떠서는 안 된다"는 지적 그대로.

## 021. '기본 서식' 도구 폐지

사용자: *"기본서식이야 뭐 내가 서식에서 하나 골라서 만들 수 있는게 아닌가요?"* —
맞는 말이라 그대로 채택. 도구·실행 함수·기본 서식 설정 창까지 걷어냈다.
**이미 팔레트에 놓여 있던 블럭도 함께 정리한다**(`palette._drop_retired_tools`) —
카탈로그에서만 빼면 이름도 실행도 없는 '모르는 키' 칸이 남는다.

## 022. 만들기 입구가 분류마다 다르다

**원인** — 창고의 ＋ 는 템플릿만 전용 창이었고 나머지는 '물감 설정' 창을 통째로
열었다. 특수기호를 만들려고 눌렀는데 서식·양식·사진 탭이 함께 뜨니, 지금 무엇을
만드는 중인지가 흐려진다. 사용자 지적: *"각 에셋별로 한 곳에서 와야합니다.
이래버리면 분류의 기준이 모호해져버리는 사고가 날 수 있습니다."*

**고침** — 분류마다 **만들기 창 하나**로 못박았다.
물감 설정 창의 '추가' 버튼도 같은 함수를 부른다 — 입구가 둘이어도 화면은 하나다.

| 분류 | 만들기 창 |
|------|-----------|
| 특수기호 | `create_char_dialog` (내장 기호 격자가 붙은 그 창) |
| 서식 | `create_style_dialog` → 팔레트의 서식 만들기 창 (026) |
| 템플릿 | `capture_template_dialog` (한글에서 선택 영역 캡처) |
| 양식 | `create_form_dialog` (hwp 파일 고르기) |

## 023. 도구의 설정

- 설정을 가진 도구는 카탈로그가 `config` 로 말한다(지금은 사진 하나).
  창고에서 그 카드를 고르면 오른쪽 판에 **[설정]** 이 붙는다.
- 사진 판에는 연결된 폴더와 장수가 함께 보인다.
- **폴더가 여럿이면 사진 버튼을 눌렀을 때 어디서 고를지 먼저 묻는다** — 이 동작은
  이미 있었으나 메뉴가 톱니 아래 고정이라 누른 곳과 뜨는 곳이 달랐다. 눌린 사진
  버튼 아래로 옮기고 '사진 폴더 관리' 항목을 더했다.

## 024. 자간 맞춤 — 없던 기능이었다

사용자가 사용법을 못 찾은 이유는 단순하다: **스파이크(실측)만 했고 기능은 만들지
않았다.** 기획서의 '탐' 줄이 "구현 가능 판정"까지였다.

이번에 `docs/SPIKE_자간보정.md` 의 방식 A 설계 그대로 구현했다.

- 도구 **'자간 맞춤'** — 팔레트에 놓고 쓴다. 선택한 문단만 손댄다.
- ⓐ 줄나눔을 **어절 단위**로 바꾼다(한글 기본값이 글자 단위라 지금도 단어가
  잘리고 있다 — 스파이크 ⑤). 잘림을 없애는 본체가 이것이다.
- ⓑ 그래서 생긴 줄 끝 빈 폭을, 다음 줄 첫 어절이 올라올 만큼 자간을 좁혀 메운다
  (−2%씩 −8%까지, **좁히기만**).
- 자간이 이미 0이 아닌 줄·표 안·마지막 줄은 건드리지 않는다. 되돌리기 한 묶음.
- 도움말에 '자간 맞춤' 절을 넣었다 — 사용법을 못 찾는 일이 다시 없게.

> **⚠ 한글 실기 확인이 남아 있다.** 스파이크는 전용 인스턴스로 실측했지만,
> 이번 구현 자체는 한글 없이 작성했다. 첫 사용 때 결과를 보고 한도(−8%)와
> 줄당 시도 횟수를 조정할 수 있다.

## 025. 수치 칸의 위아래 버튼

서식 만들기 창의 모든 수치 칸을 스핀 버튼으로 바꿨다. 눈금은 **그 값을 실제로
조정하는 단위**로 잡았다 — 줄간격 10%, 글씨크기 0.5pt, 자간 자동조절 5% 처럼
(`func_catalog.SPIN`). 이름표 폭도 넓혀 '어절단위 줄바꿈'이 안 잘리게 했다.

## 026. 창고 서식 = 팔레트 서식 조합 (합침)

**원인** — 이름은 같은 '서식'인데 코드에서 **다른 물건**이었다.
009 에서 "다르면 합치는 결정이 먼저다"라고 적어 둔 그 지점이다.

| | 예전 창고 '서식' | 예전 팔레트 '서식 조합' |
|--|--|--|
| 만드는 창 | 캡처할 항목 고르기 → 한글에서 캡처 | 조작 목록 체크 |
| 저장 모양 | `fields` (글자모양 델타) | `actions` (조작 목록) |
| 팔레트에 놓기 | **거절됨** | 됨 |

**고침 — 사용자 결정대로 팔레트 쪽으로 합쳤다.**

- 만드는 창은 **하나**(서식 만들기). 한글에서 뽑아 오고 싶으면 그 창 안의
  [한글에서 가져오기] 를 누른다 — 옛 캡처 앞단계 창은 없앴다.
- 저장은 `actions` 로 통일. **옛 `fields` 항목도 계속 읽힌다**
  (`library.style_actions` / `style_fields` 가 한 곳에서 번역).
- 창고의 서식을 **팔레트에 끌어다 놓을 수 있다**. 블럭은 `ref` 로 창고의 물감을
  가리키므로, 물감을 고치면 놓아 둔 버튼이 전부 따라 바뀐다(템플릿·양식과 같은 규칙).

## 027. [아이디어] 도구 판을 '사용법' 자리로

> **접수만 함 (2026-07-31). 코드는 건드리지 않았다.** — 사용자 지시:
> "일단 바로 수정하지말고 내가 이렇게 말하는거를 정리만 할 수 있도록 하십시오"

**사용자 원문 요지**
- 023 으로 생긴 도구 미리보기 판(이름 + 한 줄 설명 + [설정])을 보고:
  *"이거 참 좋은 생각이다. 도구의 경우에는 이렇게 사용법같은거를 옆에 띄워주는거지"*

**무엇을 말하는가**
- 다른 물감(템플릿·양식)은 오른쪽 판이 **미리보기 그림**을 보여준다. 도구는
  보여줄 그림이 없어서 지금은 이름과 한 줄 힌트만 있다.
- 그 빈자리를 **사용법**으로 채우자는 것. 도구를 고르면 "이건 이렇게 쓴다"가
  그 자리에서 읽힌다 — 도움말 창을 따로 열지 않아도 된다.
- 024(자간 맞춤)에서 겪은 문제와 같은 뿌리다: 기능이 있어도 **어디서 어떻게
  쓰는지**를 화면이 말해 주지 않으면 없는 것과 같다.

**지금 화면 (근거)**
- '라이브러리' 도구를 고른 상태: 제목 `도구`, 부제 `라이브러리 · #도구`,
  본문은 이름 + 한 줄 힌트(`등록한 서식·문자·템플릿·양식 관리`) 뿐. 판의
  아래 대부분이 비어 있다.

**정리해 둘 논점 (아직 아무것도 정하지 않음)**
1. **분량** — 한 줄 힌트를 몇 줄짜리 사용법으로 늘리는 것인가, 아니면
   도움말 한 절을 통째로 옮겨 오는 것인가.
2. **글의 출처** — 지금 힌트는 `builtin_actions` 에 있고, 절 단위 사용법은
   `help_content.py` 에 있다. 두 벌로 복사하면 반드시 한쪽만 고치는 사고가
   난다 → **한 곳에서 와야 한다**(어느 쪽인지는 결정 필요).
3. **범위** — 도구에만 둘지, 특수기호·서식처럼 그림이 없는 다른 분류에도 둘지.
4. **[설정] 과의 관계** — 사용법 글과 설정 단추가 같은 판에 어떻게 놓일지.
5. **팔레트 쪽** — 팔레트에 놓인 도구 버튼에서도 같은 글을 볼 수 있어야 하는지
   (지금은 말풍선 한 줄).

**상태**: 접수. 설계 논의 전.

## 028. [회귀] 특수기호 창에서 종류별 분류가 사라졌다

> **접수만 함 (2026-07-31). 코드는 건드리지 않았다.** — 027 과 같은 지시 아래.

**사용자 원문 요지**
- *"원래 특수기호가 종류별로 잘 정리가 되어있었는데 왜 구조가 자기 마음대로
  변경된 것인지? 종류별로 분류되어 있어야 합니다. 내가 추가한 특수기호도
  들어가야하는거고요"*

**원인 — 022 를 반영하면서 내가 합칠 방향을 잘못 골랐다**

022 는 "각 에셋별로 만들기 창이 하나여야 한다"는 요구였다. 특수기호에는 창이
두 벌 있었는데, **기능이 적은 쪽으로 합쳐 버렸다.**

| | 물감 설정 '특수기호' 탭 (원래 쓰던 것) | 팔레트 빈칸용 `_CharDialog` (합친 결과) |
|--|--|--|
| 종류별 분류 | **있다** — 왼쪽에 묶음 목록 12종<br>(전체 · 내가 등록 · 원문자·숫자 · 원문자·알파벳 · 원문자·한글 · 로마숫자 · 낫표 · 괄호숫자 · 괄호한글 · 괄호한자 · 그리스 · 수학 …) | **없다** — 검색칸 하나 |
| 내가 등록한 기호 | **보인다** ('전체'·'내가 등록' 묶음) | **안 보인다** — 내장 기호만 |
| 한 번에 보이는 수 | 묶음을 고르면 그 묶음 전부 | 425개 중 **앞 96개만** |

즉 사용자가 잃은 것은 두 가지다: **묶음 목록**과 **내가 등록한 기호**.
"자기 마음대로 변경"이 맞다 — 026(서식)은 사용자가 *"팔레트가 기본이 되어야
합니다"* 라고 **명시**했지만, 특수기호에는 그런 지시가 없었는데 같은 원칙을
내가 확대 적용했다. 026 의 근거를 022 에까지 늘려 쓴 것이 잘못이다.

**돌려놓아야 할 것 (요구 사항)**
1. **종류별 묶음 목록**이 특수기호 만들기 창에 있어야 한다.
2. **내가 등록한 특수기호**가 그 목록에 함께 들어가야 한다.

**정리해 둘 논점 (아직 아무것도 정하지 않음)**
- 합치는 방향을 **반대로** 잡는다: 묶음 목록이 있는 쪽(물감 설정 탭의 격자)을
  기준으로 삼고, 팔레트 빈칸에서 열어도 같은 화면이 나오게 한다.
  → 022 의 "입구가 어디든 창은 하나"는 그대로 지키면서 기능이 안 줄어든다.
- 그 창은 지금 두 가지 일을 한다: **블럭 만들기**(고른 기호를 입력칸에 담기)와
  **물감 등록**(창고에 넣기). 격자를 공유하되 이 둘을 어떻게 가를지 결정 필요.
- 425개 격자의 **버벅임 대책**(나눠 그리기)이 물감 설정 쪽에는 이미 있다
  (`_render_char_grid`). 옮겨 쓸 때 함께 가져와야 한다.
- 96개 제한은 묶음이 생기면 필요 없어진다 — 묶음 하나가 그보다 작다.

**상태**: 접수. 내 잘못으로 생긴 회귀라 우선순위 높음. 지시 대기.

## 029. 사진 도구 — 폴더 연결을 **판 안에서** 하게

> **접수만 함 (2026-08-01). 코드는 건드리지 않았다.**

**사용자 원문 요지**
- *"여기 사진 도구 관련해서 전혀 바뀐게 없네? 내가 사진의 경우에는 폴더 연결할
  수 있어야 한다고 했는데 아무 변화가 없네? 옆에 있는 공간을 활용하면 될 것
  같은데 한번 검토해보자"*

**확인한 사실 (실측)**
- [설정] 단추는 동작한다. 다만 여는 것이 **'물감 설정' 창 통째로**다 —
  실측: `LibraryManager` 가 뜨고 탭 버튼이 `['서식','특수기호','템플릿','양식','사진']`
  다섯 개. 사진 탭이 켜진 채로 열리기는 한다.

  "바뀐 게 없다"가 정확한 관찰이다. 023 은 **현황 표시**만 판에 올렸을 뿐,

## 031. [버그] 양식 수정 — 버벅임 · 끝난 뒤 창이 커짐 · 빈 문서가 남음

> **접수만 함 (2026-08-01). 코드는 건드리지 않았다.**
> 사용자 지시: *"내가 명시적으로 고치라고 하기 전까지는 코드 수정을 해서는 안됩니다."*

**사용자 원문 요지**
- *"양식수정이 또 말썽입니다. 엄청 버벅거리네요."*
- *"양식 수정이 끝난 다음에 창이 커져버리고 필요없는 빈 문서가 남습니다."*
- *"이제 기능 수정을 안할 터이니 이런 버그를 잡아야 합니다."*

### 031-a. 끝난 뒤 창이 커진다 — **원인 거의 확정**

`_exit_dock_layout()` (palette_ui) 이 접어 뒀던 격자·창고를 다시 `pack()` 한
**직후 곧바로** `_fit_window()` 를 부른다. 그런데 `_fit_window` 는 스스로
`update_idletasks()` 를 하지 않는다 — 머리말에 이유가 적혀 있다:

> "앞머리의 update_idletasks 는 뺐다 (2026-07-31) — **호출부가 전부 after_idle
> 로 미루므로** 여기 올 때는 레이아웃이 이미 정리돼 있어…"

**그 전제가 이 호출부에서만 깨져 있다.** `_exit_dock_layout` 은 after_idle 로
미루지 않고 동기로 부른다. 그래서 재는 값(`winfo_reqheight`)이 아직 **편집
때의 큰 레이아웃**이고, 그 값이 그대로

```python
self.minsize(self.winfo_reqwidth(), self.winfo_reqheight())   # ← 큰 값이 굳는다
self.geometry("")                                             # ← 큰 크기로 적용
```

로 들어간다. minsize 에 박히므로 **그 뒤로는 창을 줄일 수도 없다.**
사진 2 의 세로로 길어진 창이 이 모양과 일치한다.

곁가지 두 개 (같이 봐야 함):
- `_fit_window` 의 `if req == self._last_req: return` 이른 반환 — 값이 우연히
  같으면 minsize 갱신 자체를 건너뛴다.
- `_collapse_for_edit` 이 저장하는 `zoom_h = zoom_pane.cget("height")` 는
  **한 번도 지정된 적 없는 값이라 0** 이다(판 높이는 `fill="y"` 로 옆 판이
  정해 준다). 되돌릴 때 0 을 넣는 것 자체는 맞지만, 위 타이밍 문제와 겹치면
  판단이 어려워진다.

### 031-b. 빈 문서가 남는다

`hide_window_if_ours(windows_before)` 는 **고치기 전에 없던 창일 때만** 숨긴다.
한글이 이미 떠 있었으면(=`windows_before` 에 핸들이 있으면) 손대지 않는다 —
"사용자 창을 뺏지 않는다"는 규칙이라 그 자체는 옳다.

화면(사진 1)에는 한글 탭이 **둘**이다: `빈 문서 1` + `편집중_db79d88f_….hwp`.
편집 탭이 닫히면 `빈 문서 1` 만 남는다. 확인할 것:
- 그 `빈 문서 1` 이 **원래 사용자 것**인지, 우리가 `ensure_visible`/`connect`
  로 켜면서 딸려온 바탕 문서인지.
- 후자라면 `windows_before` 판정이 그 경우를 못 가른다는 뜻이다
  (창은 전부터 보였는데 **문서**는 우리가 만든 것).

### 031-c. 버벅임

아직 원인을 못 잡았다. 짚어 볼 곳:
- `hwp_dock.Dock._follow_loop` — 이벤트 훅 + **200ms 안전망마다** `_snap()` 과
  `keep_order()`. `keep_order` 는 `SetWindowPos` 를 두 번 부르고 `is_hung`
  검사까지 한다. 훅이 자주 오면 그때마다 `_snap()` → `_punch_hole()`
  (`SetWindowRgn`) 이 함께 돈다.
- 훅 등록 실패 시 `_poll_fallback` 은 **8ms 폴링**이다 — 이 경로로 빠졌는지
  로그(`도킹 이벤트 훅 등록 실패`) 확인 필요.
- 버벅임이 **한글 쪽**인지 **우리 창 쪽**인지부터 갈라야 한다.

**상태 (2026-08-01 파트 1)**: **031-a 수정 완료.** `_fit_window(settle=True)` —
판을 통째로 접었다 펴는 두 자리(`_collapse_for_edit`·`_exit_dock_layout`)에서만
스스로 `update_idletasks()` 하고 이른 반환도 건너뛴다. "호출부가 전부 after_idle
로 미룬다"는 전제가 **거기서만 깨져 있었다** — 그 두 곳은 다음 줄이 바로 창
크기에 기대므로 미룰 수가 없다. 이제 편집 때의 큰 높이가 `minsize` 에 박히지
않는다.

**031-b·c 는 따로 고치지 않았다** — 예측대로 032 에 딸려 풀리는 자리다.
메인 도킹이 제자리로 복귀하면 그 `빈 문서 1` 은 '주인 있는 문서'가 되고,
버벅임의 정체였던 **Dock 둘의 SetWindowPos 왕복**은 소유권 대장이 없앴다.
덧붙여 이 라운드에서 **구멍 뚫기가 여태 죽어 있었다**는 것을 찾았다(035 항목
참고) — 도킹이 z 순서 하나에만 기대고 있었으니 잰크의 몫도 거기 있었다.
**실기 검증에서 확인할 항목**으로 남긴다.

## 032. [계획] 도킹 소유권 위계 — 한글 창의 주인은 한 번에 하나

> **계획만 세움 (2026-08-01, 사용자 지시: "어떻게 해결할 것인지 계획만 세워놓으십시오"). 코드는 건드리지 않았다.**

**사용자 원문 요지**
- 빈 문서를 열어 메인 창에 도킹한 상태에서, 양식이 원하는 대로 안 불려와 **양식 수정**을 띄웠다.
- 그러자 "한글파일이 붙어야 하는 도킹의 대상이 두 개가 되어버리니 **두 상황을 왕복하면서 버벅거리는** 문제"가 생겼다.
- "도킹의 대상이 두 개(메인 화면, 양식 수정)인 경우 **양식 수정에 붙어야** 합니다. 이런 위계를 세우지 않으면 두 창이 동시에 도킹 요청을 하기 때문에 버벅이게 됩니다."

**원인 (코드로 확인)**

`hwp_dock.Dock` 인스턴스가 **둘** 살아 있을 수 있다:
- 메인 도킹 — `app.py` `_enter_dock()` 이 만든 `_dock["dock"]`
- 양식 수정 — `palette_ui._enter_dock_layout()` 이 만든 `self._dock`

둘 다 같은 한글 hwnd 를 **자기 판 자리로** SetWindowPos 한다. 따라가기 틱마다
한글 창이 두 자리를 왕복 — 사용자가 본 버벅임 그대로다. 031-c(양식 수정
버벅임)의 유력 원인 후보이기도 하다(재현 경로가 "메인 도킹 중 양식 수정").
※ 도킹 없이도 버벅이면 031-c 의 훅/폴링 쪽 원인이 따로 남는다.

**해결 원칙 (사용자 결정)**

한글 창의 도킹 주인은 **한 번에 하나**. 겹치면 **더 구체적인 작업이 이긴다** —
양식 수정(편집 세션) > 메인 도킹.

**설계 계획**

1. **소유권 대장을 `hwp_dock` 모듈에 둔다** — 두 호출부(app·palette_ui)가
   서로를 모르므로, 공용으로 쓰는 모듈이 심판이 돼야 한다.
   - `claim(dock, priority)` / `release(dock)` — 스택(LIFO).
   - 높은 우선순위가 오면 지금 주인을 `pause()` 하고 새 주인이 잡는다.
   - 새 주인이 `release()` 하면 스택의 이전 주인을 `resume()`.
2. **우선순위**: 양식 수정·내용 고치기(편집 세션) 100 > 메인 도킹 10.
   (문서 해체 판은 설정 창 안이라 메인 도킹과 동시일 수 없음 — 구현 때 확인만)
3. **pause / resume**:
   - pause = `stop_follow()` 만 — 창 복원(restore)은 **하지 않는다**. 새 주인이
     바로 이어받으므로 제자리로 튕겼다 다시 붙는 깜빡임이 없어야 한다.
   - resume = hwnd 유효성 확인(한글이 그새 닫혔을 수 있다) → `ensure_visible()`
     → `start()`. 죽었으면 조용히 도킹 해제 상태로 정리하고 알림 하나.
4. **반대 방향은 차단**: 양식 수정이 주인일 때 메인 ◫ 를 누르면 뺏지 않고
   안내한다 — "양식 수정이 한글을 쓰고 있습니다. 저장하거나 취소하면
   도킹할 수 있습니다." (메인이 **이전 주인**이었다면 스택이 알아서 복귀시키므로
   이 안내는 '도킹 없이 양식 수정부터 연' 경우에만 뜬다)
5. **수정 지점**:
   - `hwp_palette/hwp/hwp_dock.py` — 대장(claim/release/pause/resume)
   - `hwp_palette/app.py` `_enter_dock` / `_exit_dock` — claim(10)/release + 차단 안내
   - `hwp_palette/ui/palette_ui.py` `_enter_dock_layout` / `_exit_dock_layout` — claim(100)/release

**검증 계획**
- 순수 유닛테스트: 가짜 Dock 로 소유권 스택 규칙(claim→pause, release→resume,
  이중 release 안전, 주인 아닌 release 무시)을 못박는다.
- 실기 시나리오 셋: ① 메인 도킹 → 양식 수정 → 저장 → **메인 자동 복귀**
  ② 같은 경로에서 취소 ③ 도킹 없이 양식 수정 → 끝 → 아무 일 없음.
- 버벅임 판정: 편집 중 SetWindowPos 를 부르는 주체가 하나뿐인지 로그로 확인.

**상태 (2026-08-01 파트 1)**: **완료.** 계획대로 `hwp_dock` 에 소유권 대장을 뒀다.

- `claim(dock, priority, on_resume)` / `release(dock)` — LIFO 스택,
  `PRIORITY_EDIT=100` > `PRIORITY_MAIN=10`.
- pause 는 `stop_follow()` 만 (창 복원 없음 — 깜빡임 방지),
  resume 은 `IsWindow` 확인 → `on_resume()`(=`ensure_visible`) → `start()`.
- 낮은 쪽은 **뺏지 않는다**: 편집이 주인일 때 메인 ◫ 는 뺏지도 **떼지도** 않고

## 033. [분석] 수능양식 — 빈칸 2개 중 1개만 채우기 창에 보인다

> **분석만 함 (2026-08-01). 코드는 건드리지 않았다.** 실제 수능양식 조각을
> 임시 사본으로 열어 실측했다 (원본 무변경).

**사용자 원문 요지**
- 빈칸 지정 `\` 둘 + 자리 지정 `\본문\` 인 상황에서 "충돌이 발생하는 것
  같습니다. 빈칸을 하나만 인식하는 상황".

### 033-a. 원인 — `\본문\` 충돌이 아니라 **판독기 불일치**다 (실측 확정)

수능양식 조각(fragments/31354095….hwp)을 두 판독기로 각각 읽었다:

| 판독기 | 쓰는 곳 | 읽은 것 |
|---|---|---|
| `GetTextFile("TEXT")` | **등록할 때** 빈칸 세기 (count_slots) | `\` · `\` · `\본문\` → **빈칸 2** ✔ (카드의 "빈칸 2") |
| HWPX run 스캔 (form_fill.read_runs) | **채우기 창**이 자리 뽑기 | `\` 1개 + `\본문\` 뿐 → **빈칸 1** ← 창의 "채울 자리 1개" |

`\본문\` 은 두 쪽 모두에서 올바르게 제외된다(RESERVED_NAMES) — 충돌이 아니다.
**둘째 `\` 가 HWPX run 스캐너(RUN_RE)가 못 여는 곳에 들어 있다** — 화면상
크게 기울어 그려진 그 `\` 로, 글상자/그리기 개체 안 텍스트로 추정된다.
`GetTextFile` 은 개체 안 글자까지 주지만 RUN_RE 는 본문 `<hp:t>` 만 읽는다.
form_fill 에 `_hidden_token_count`("RUN_RE 가 못 여는 조각 속의 자리 토큰 수,
경고용")가 이미 있다는 것 자체가 이 한계를 알고 있었다는 뜻이다 — 다만
그 경고가 **채우기 창 화면까지 나오지 않는다.**

**고칠 방향 (지시 대기)**
1. 실측 한 걸음 더: 그 `\` 가 HWPX 의 어떤 요소 안에 있는지 확인
   (검사 스크립트로 부모 태그 추적) → RUN_RE/read_runs 를 개체 안
   `<hp:t>` 까지 넓힌다. **재주입(되쓰기)도 같은 경로로 안전한지 실측** —
   읽기만 넓히고 쓰기가 못 따라가면 반쪽이다.
2. 그 전까지의 안전망: 채우기 창 머리에 불일치를 그대로 말한다 —
   "등록된 빈칸 2개 중 1개는 글상자 안에 있어 여기서 못 채웁니다"
   (_hidden_token_count 활용). 지금은 "채울 자리 1개"라고만 해서
   사용자가 등록 개수와 다른 것을 알 길이 없다.
3. 등록 시점 통일: 등록할 때도 같은 스캐너로 세거나, 두 값이 다르면
   등록 창에서 미리 경고한다.

### 033-b. "왼쪽 버튼을 눌러도 반응이 없다" — 그 규칙은 이것이었다

기억하시려던 규칙 (2026-07-31 확정, plan-post-0.3.0.html 무인 진행 규약 + H-5):

- **왼쪽 클릭 = 빈칸인 채로 실행** (템플릿·꾸러미는 빈칸으로 꽂기.
  양식은 자리가 있으면 채우기 표, 없으면 그냥 열기 — 그대로 인쇄하면
  `\` 가 찍히는 게 맞는 동작이다)
- **채워서 꽂기 = 우클릭 메뉴** ("기존 양식 채우기 창 재사용") — 그런데
  이 우클릭 입구는 **잔결정 목록에만 있고 아직 구현되지 않았다.**
  눌러도 반응이 없는 것의 정체다.

## 034. [계획] 자간 맞춤 — 표 안에서도 동작해야 한다

> **분석 + 계획만 (2026-08-01). 코드는 건드리지 않았다.**

**사용자 원문**: "표 안이라도 해도 자간맞춤 기능이 구현이 되어야 합니다."
(보기 박스 — 표 안의 ㄱ 문단을 선택해 실행 → "다듬을 문단을 찾지 못했습니다
(표 안은 제외됩니다)")

### 원인 — 문 하나가 막고 있다

`engine_library._selected_para_range()` 가 선택의 양끝이 **본문(list 0)** 일
때만 범위를 준다. 표 셀·글상자는 list 번호가 달라 여기서 None → "찾지 못함".
그 아래 전체(`_set_break_by_word`·`_read_spacing`·`_apply_spacing`·
`_tighten_para`)도 `SetPos(0, para, …)` 로 **list 0 을 박아** 쓴다.

### 왜 뺐었나 — 그리고 그 이유가 이제 약하다

주석: "셀마다 폭이 달라 기준 폭 계산이 통째로 달라진다 (스파이크 '남은 위험')".
그런데 **실제 구현은 폭을 재지 않는다** — 자간을 한 단계 좁혀 보고 다음 줄
첫 어절이 끌려 올라왔는지를 `_line_bounds` 로 관찰하는 '해 보고 확인' 방식이다.
이 방식은 그릇의 폭과 무관하게 동작하므로, 셀 폭 우려는 이 구현에는 해당하지
않는다. 남는 것은 좌표 배관 문제뿐이다.

### 계획

1. `_selected_para_range()` → `(list_id, first, last)` 로 확장.
   조건을 "양끝 list 가 **같으면**"으로 완화 (0 강요 제거) — 셀 하나 안의
   선택이 통과된다.
2. `list_id` 를 배관 전체에 꿴다: `_set_break_by_word`·`_read_spacing`·
   `_apply_spacing`·`_line_bounds`·`_tighten_para`·`fit_line_spacing` 의
   `SetPos(0, …)` → `SetPos(list_id, …)`.
3. 경계 방어 보강: 줄 끝에서 MoveRight 가 **다음 셀로 튀는** 경우를
   막아야 한다 — 이미 있는 `nxt[1] != para` 멈춤에 `nxt[0] != list_id` 를
   더한다.
4. **여러 셀에 걸친 선택은 1차 제외** — 셀 블럭 선택은 GetSelectedPos 의
   모양부터 다르다. "셀 하나씩 선택해 주세요" 안내로 막고, 셀 순회는 후속.
5. 실측 3건 (구현 전 스파이크):
   ① 셀 안에서 MoveLineBegin/MoveSelLineEnd/MoveRight 이동이 본문과 같게
      노는가 ② `SelectText` 가 셀 좌표에서 동작하는가 (안 되면 이미 있는
      MoveSelRight 대체 경로 사용) ③ 어절 단위(ParagraphShape) 적용이 셀
      문단에도 같은 액션으로 먹는가.
6. 검증: 실기 — 보기 박스(ㄱㄴㄷ) 문단에 실행 → 잘림 해소 확인, ↺ 한 번에
   원복 확인. 회귀 테스트는 list_id 배관의 순수 부분만.

**상태**: 원인 확정 · 계획 완료. **고치라는 지시를 기다린다**
(031·032·033 라운드에 같이 묶을 수 있으나 이 건은 engine_library 만 만져
독립 진행도 가능).

## 035. [버그] 도킹 중 팔레트 드롭다운을 열면 도킹된 화면이 안 보인다

> **원인 조사·수정 방안만 (2026-08-01). 코드는 건드리지 않았다.**
> 사용자 지시: *"원인을 파악하고 수정방안에 대해서 고려해두십시오."*

**사용자 원문 요지**
- *"도킹된 상태에서 팔레트를 옮겨가려고 드롭다운을 누르니까 도킹되어있던 화면이
  보이지 않게 되는 버그가 발생했습니다."*
- 화면: 팔레트 고르개(`_pal_menu` 의 Popover)가 열려 있고, 그 아래 도킹 자리가
  **통째로 하얗다**. 도구줄과 팔레트 버튼 줄은 정상.

### 도킹이 어떻게 그려지는지부터 (원인을 읽으려면 필요)

`hwp_dock` 은 한글을 우리 창 **위로 올리지 않는다.** 대신 우리 창에서 판
자리를 **오려 낸다**(`_punch_hole` → `SetWindowRgn`). 그 자리에 창이 아예
없으므로, 같은 좌표에 맞춰 둔(`_snap`) 한글이 그대로 비쳐 보인다.
z 순서는 `keep_order` 가 따로 잡는다 — **한글을 맨 위, 우리 창을 그 바로 아래**.

### 원인 후보 — 둘 다 같은 뿌리(팝오버가 '제3의 창')다

**후보 ①: `keep_order` 가 팝오버를 남의 창으로 본다 (유력)**

```python
fg = win32gui.GetForegroundWindow()
if not force and fg not in (self.hwnd, self._root_hwnd):
    return                      # 남의 프로그램을 쓰는 중 — 건드리지 않는다
```

팝오버는 **자체 hwnd 를 가진 Toplevel** 이다(`overrideredirect` + `grab_set`).
그것이 활성이 되는 순간 `fg` 는 한글도 우리 메인 창도 아니다 → **위 줄에서
그냥 돌아간다.** 200ms 안전망이 도는 내내 순서를 다시 잡지 않는다.
그 사이 팝오버 활성화로 우리 창 무리가 앞으로 나오면 한글은 뒤로 밀리고,
다시 올려 줄 사람이 없다.

이 판정은 **소유 관계를 안 본다**는 것이 핵심이다. 팝오버·대화상자는 우리 창이
소유(owner)한 창이라 사실상 '우리 편'인데, 핸들 두 개와만 비교하니 남으로 읽힌다.
같은 이유로 **대화상자를 띄우는 다른 경로에서도 같은 증상이 나야 정상**이다
(재현 확인 대상).

**후보 ②: 구멍이 지워지거나 어긋난다**

화면이 '하얗다'는 것은 구멍 **아래의 한글이 안 보인다**는 뜻도 되지만,
구멍이 아예 **메워져 우리 판(host Frame)의 배경이 그려진** 모습일 수도 있다.
둘은 화면만 봐서는 못 가른다.
`_snap()` 이 틱마다 `_punch_hole()` 을 부르므로 구멍은 스스로 낫는 구조인데,
그 틱이 돌지 않는 상황(스레드 이상)이라면 ①과 겹쳐 나타난다.

### 무엇을 재면 갈리나 (스파이크 1건)

팝오버를 여는 순간 다음을 로그로 남기면 ①/② 가 즉시 갈린다:
- `GetForegroundWindow()` 와 그 창의 `GetAncestor(GA_ROOTOWNER)`
- `_root_hwnd` · `hwnd`(한글) 의 z 순서 (`GetWindow(GW_HWNDPREV)` 사슬)
- `GetWindowRgn` 으로 구멍이 살아 있는지, `_snap` 틱이 도는지

### 수정 방안 (둘 다 덮는다)

1. **`keep_order` 의 '우리 편' 판정을 소유 사슬로 넓힌다.**
   `fg` 를 그대로 비교하지 말고 `GetAncestor(fg, GA_ROOTOWNER)` 를 구해
   `_root_hwnd` 와 같으면 우리 편으로 본다 — 팝오버·대화상자·툴팁이 전부 포함된다.
   (한글 쪽도 같은 방식으로 넓히면 한글의 하위 대화상자까지 덮인다)
2. **팝오버가 뜰 때 한 번은 강제로 순서를 잡는다.** 팝오버는 `<Activate>` 를
   우리 메인 창에 주지 않으므로 지금은 재조정 계기가 없다. 도킹 중이면
   팝오버 `show()` 직후 `keep_order(force=True)` 를 한 번 부르는 갈래가 필요하다
   (`hwp_dock` 에 “지금 도킹 주인” 이 있으면 그쪽에 알리는 식 — **032 의 소유권
   대장이 들어오면 그 대장이 그 자리를 맡는 것이 자연스럽다**).
3. 구멍이 원인으로 확인되면 `_punch_hole` 을 팝오버 열림에도 태운다(2 와 같은 자리).

### 032 와의 관계

같은 파일(`hwp_dock.py`)·같은 개념(도킹 주인과 z 순서)을 만진다.
**032 라운드에 함께 넣는 것이 맞다** — 따로 하면 `keep_order` 를 두 번 고친다.

**상태 (2026-08-01 파트 1)**: **완료 — 실측 대신 코드에서 답이 나왔다.**

후보 ②(구멍이 없다)가 **사실이었다.** `_punch_hole` 과 `clear_crop` 이 쓰는
`dpi_scale()` 과 `_RGN_DIFF` 의 **정의만** 커밋 `e84cc46`(제목줄 잘라내기 철회)
에서 지워지고 호출부는 남아 있었다. 그 뒤로 구멍 뚫기는 **매번 NameError 로
실패**했고 `except` 가 삼켜 로그에만 남았다 — 도킹 화면은 여태 `keep_order` 의
z 순서 **하나에만** 기대고 있었던 셈이다. 순서가 흔들리는 순간(팝오버·항상 위)
그 자리에 비칠 것이 없어져 하얗게 보였다. 정의를 되살렸다.

후보 ①도 함께 고쳤다: `keep_order` 의 '우리 편' 판정을 `_is_ours()` 로 빼고
`GetAncestor(fg, GA_ROOTOWNER)` 까지 본다 — 팝오버·대화상자·툴팁이 전부 포함된다.
더해서 판이 뜰 때 순서를 한 번 강제한다: `popover.on_shown()` 갈고리에
`hwp_dock.reorder_now()` 를 걸었다 (design 층이 hwp 층을 직접 부르지 않게).

## 036. [버그] 도킹 중 한글을 클릭하지 않은 채 키를 누르면 도킹 화면이 사라진다

> **원인 조사·수정 방안만 (2026-08-01). 코드는 건드리지 않았다.**

**사용자 원문 요지**
- *"한글파일이 클릭으로 지정되지 않은 상황에서 키보드를 누르니까 도킹된 화면이
  안 보이는 버그가 발생합니다."*

### 원인 — **PageUp 이 '항상 위' 토글이고, 그것이 도킹의 순서 계약과 정면으로 부딪친다**

두 사실이 만나서 난다.

**하나.** 앱은 `PageUp` 을 **단독키**로 전역에 걸어 두었다 (2026-07-31 결정).

```python
root.bind_all("<Prior>", _on_pageup)   # Tk 에서 PageUp 은 <Prior>
# → _toggle_top() → root.attributes("-topmost", on/off)
```

입력칸에 포커스가 있을 때만 비켜 준다. **도킹 중은 예외 목록에 없다.**

**둘.** 도킹은 z 순서에 **엄격한 계약**을 건다 (`hwp_dock.keep_order`):

```python
SetWindowPos(한글,  HWND_TOP, …)      # 한글을 맨 위로
SetWindowPos(우리창, 한글,     …)      # 우리 창은 한글 **바로 아래**
```

우리 창이 `-topmost` 가 되면 **최상위 띠**로 올라간다. 그 띠에 있는 창 아래로
평범한 창(한글)을 넣을 수 없으므로, 위 두 줄은 매 틱(200ms) **이길 수 없는
싸움**을 반복한다. 도킹 판은 구멍(`SetWindowRgn`)으로 오려 낸 자리라, 순서가
어긋나는 순간 그 자리에 비칠 것이 없어져 **하얗게 보인다.**

**왜 하필 "한글을 클릭하지 않은 상황"인가** — 그게 조건의 핵심이다.
한글을 클릭해 뒀으면 키는 한글이 받아 우리 바인딩이 아예 안 돈다.
클릭하지 않았으면 포커스는 우리 창에 있고, 사용자는 **눈앞에 보이는 한글 문서를
스크롤하려고** PageUp 을 누른다 — 그 키가 '항상 위 토글'로 먹는다.
사용자가 의도한 것과 실제로 일어난 일이 완전히 다르다.

### 035 와 같은 뿌리

035(팝오버)와 036(PageUp)은 **둘 다 z 순서의 주인이 둘이 되는 문제**다.
도킹은 순서를 스스로 관리하는데, 바깥에서 순서를 흔드는 길이 두 개 열려 있다.

### 수정 방안

1. **도킹 중에는 z 순서의 주인을 하나로 못박는다.**
   도킹에 들어갈 때 `-topmost` 를 **끄고 그 값을 기억**했다가, 도킹을 뗄 때
   되돌린다. 도킹 중 순서는 `keep_order` 만 정한다.
2. **도킹 중 PageUp 은 비켜 준다.** 입력칸 예외와 같은 자리에 "도킹 중" 조건을
   더한다. 눌러도 아무 일이 없는 대신 안내 한 줄:
   "도킹 중에는 '항상 위'를 바꿀 수 없습니다 — 도킹을 뗀 뒤 바꿔 주세요."
   (도구줄의 ⇧ 버튼도 같은 규칙 — 버튼만 막고 키를 열어 두면 같은 사고가 난다)
3. **035 와 공통**: `keep_order` 의 '우리 편' 판정을 `GetAncestor(fg, GA_ROOTOWNER)`
   기준으로 넓혀, 팝오버·대화상자가 활성일 때도 순서를 다시 잡게 한다.
4. **더 볼 것(후속)**: 도킹 중 우리 창이 키 포커스를 갖는 것 자체가 헷갈림의
   원인이다. 도킹 중에는 판을 눌렀을 때 한글로 초점을 넘기는 편이 자연스럽다 —
   이번 라운드 범위 밖으로 두고 별도 검토.

### 검증

- 실기: 도킹 → 한글을 클릭하지 않은 채 PageUp → **도킹이 그대로 유지**되고
  안내가 뜬다. 도킹을 떼면 PageUp 이 다시 '항상 위'로 동작한다.
- 회귀: 도킹이 아닐 때 PageUp 토글은 그대로 (기존 동작 보존).

**상태 (2026-08-01 파트 1)**: **완료.** 방안 셋을 그대로 넣었다.

1. 도킹에 들어갈 때 끈 `-topmost` 를 `_dock["was_topmost"]` 에 **기억했다가**
   뗄 때 되돌린다 (여태는 끄기만 했다).
2. **도킹 중에는 '항상 위'를 바꿀 수 없다** — 버튼(⇧)과 키(PageUp)가 같은
   길(`_toggle_top`)로 들어오므로 거기 한 곳에서 막고 안내 한 줄을 띄운다.
   값 저장(`set_config_value`)보다 **먼저** 막는다 — 뒤면 상태만 어긋난 채 남는다.
3. `keep_order` 의 '우리 편' 판정을 소유 사슬로 넓혔다 (035 와 공통).

후속(도킹 중 키 포커스를 한글로 넘기기)은 계획대로 이번 범위 밖.

## 037. [계획] 한 칸에 여러 물감이 든 것을 **겉에서 알 수 있게** — 세로 띠

> **계획만 (2026-08-01, 사용자 지시: "어떻게 반영을 할 것인지 계획해놓으십시오").
> 코드는 건드리지 않았다.**

**사용자 원문 요지**
- *"이 경우에 답안 하나 안에 다양한 물감이 들어간 상황인데 예전에 이런 경우에는
  옆에 세로로 MIX라는 띠를 달아준다고 했었는데 전혀 반영이 안 된 상황입니다."*
- 화면: 개인 팔레트의 **답안** 칸을 누르면 1행답안·2행답안·3행답안·5행답안·
  3행답안표·5행답안표 여섯이 팝오버로 뜬다. 그런데 칸 겉면은 그냥 `답안` 글자뿐이다.

### 왜 안 붙어 있나 — **결정이 두 번 갈렸다** (사실 확인)

이 화면의 `답안` 은 **겹친 칸(group)** 이다 — 누르면 안에서 **하나를 고른다**.
프로그램 안에서 이것과 **섞기(MIX)** 는 다른 물건이다:

| | 겹치기 (group) | 섞기 (MIX · 꾸러미) |
|--|--|--|
| 뜻 | 한 칸에 포개 두고 **택일** | 여러 물감을 이어 붙여 **합체** |
| 근거 | 피드백 018 · 기획서 2-6 | 피드백 017 · 기획서 2-5 |
| 표시 계획 | “겹친 종이 모양 + 개수 배지” | “칸 오른쪽 **세로 MIX 리본**, 칸 높이 불변” |
| 지금 상태 | **아무 표시 없음** | 리본 있음 — 단, **물감 창고 카드에만** |

두 가지가 겹쳐 “전혀 반영이 안 된” 상태가 됐다.

1. **겹친 칸 표시는 결정이 뒤집혔다.** 018 의 “겹친 종이 + 개수 배지”가
   기획서의 <b>무인 진행 규약(2026-07-31) 잔결정 표</b>에서
   <code>겹친 칸 겉면 → 그룹 이름만</code> 으로 정해지면서 빠졌다.
   지금 코드는 그 결정을 그대로 따르고 있다 (`app._block_label` 의
   “겹친 칸은 그룹 이름만 보인다 (무인 진행 규약 2026-07-31)”).
   → **이번 지시가 그 잔결정을 뒤집는 것이다.**
2. **MIX 리본은 창고 카드에만 있다.** `store_ui._tile` 한 곳뿐이고
   (`grep MIX` 결과 코드 전체에서 그 한 줄), 팔레트 버튼에는 원래 계획에도
   없었다. 그래서 섞은 물감을 팔레트에 놓아도 겉면에는 표시가 없다 —
   **이 문제도 같이 남아 있다.**

### 표기를 어떻게 할 것인가 (정할 것)

사용자가 기억하는 것은 “세로 띠”다. 그 형태는 그대로 가되, **겹치기와 섞기는
다른 물건이라 같은 글자를 쓰면 서로를 가린다.** 세 안:

| 안 | 겹친 칸 | 섞은 물감 | 평가 |
|--|--|--|--|
| A | `MIX` 띠 | `MIX` 띠 | 가장 단순. 하지만 **택일과 합체가 같은 표시**가 된다 |
| B | 개수만 세로로 (`6`) | `MIX` 띠 | 구분됨. 겹친 칸은 “몇 개 들었나”가 실제로 궁금한 정보 |
| C | `겹침` 띠 + 개수 | `MIX` 띠 | 가장 분명. 띠가 넓어져 좁은 칸에서 부담 |

**권함: B.** 겹친 칸에서 알고 싶은 것은 “여러 개가 들었다”와 “몇 개냐”이고,
그 둘을 숫자 하나가 동시에 말한다. 섞은 물감은 `MIX` 로 남겨 두 개념이 갈린다.
띠의 **색으로도 가른다** — 섞기는 지금의 보라(`MIX_BG/MIX_FG`), 겹치기는 다른 계열.

### 어디에 붙일 것인가 — **세 화면이 같은 규칙이어야 한다**

지금은 창고 카드 한 곳만 리본이 있어, 같은 물감이 화면마다 다르게 보인다.

| 화면 | 지금 | 계획 |
|--|--|--|
| 물감 창고 카드 | MIX 리본 있음 | 그대로 + 겹침은 창고에 없음(겹침은 배치라 창고엔 낱개) |
| 설정 창 격자 타일 | 없음 | 겹침 띠 · MIX 띠 둘 다 |
| 메인 창 팔레트 버튼 | 없음 | 겹침 띠 · MIX 띠 둘 다 |

### 구현 계획

1. **공용 부품 하나로 만든다** — `design/` 에 “칸 오른쪽 세로 띠”를 그리는
   부품을 두고 세 화면이 그것을 쓴다. 지금처럼 창고에만 손으로 그려 두면
   또 한 화면만 바뀐다. (030 의 ‘자체 부품’ 방향과 같은 자리 — **함께 하면 이득**)
2. **RoundButton 에 띠를 얹는 길**을 낸다. 팔레트 버튼은 `RoundButton`(Canvas)이라
   창고 카드처럼 `place()` 로 라벨을 얹을 수 없다 — 캔버스에 직접 그리는
   `set_ribbon(text, bg, fg)` 같은 통로가 필요하다.
   <b>칸 높이·폭은 불변</b>(2026-07-31 결정)이므로 띠는 오른쪽 안쪽으로만 들어간다.
3. **판정은 한 곳에서** — “이 블럭이 여럿을 담았는가”를 묻는 함수를 만들어
   (`group` 이면 `len(items)`, 템플릿이 꾸러미면 `MIX`) 세 화면이 같은 답을 쓴다.
   지금은 창고만 `item.get("mix")` 를 직접 본다.
4. **좁은 칸 대비** — 1칸짜리 블럭에서 띠가 이름을 덮지 않는지 확인.
   덮으면 띠를 더 얇게 하거나 아이콘 자리와 맞바꾼다.

### 검증

- 눈으로: 메인·설정·창고 세 화면에서 같은 물감이 **같은 표시**로 보이는지.
- 칸 높이가 낱개 블럭과 **똑같은지**(들쭉날쭉 금지 — 2026-07-31 결정의 핵심).
- 1칸·2칸·3칸 폭과 한 줄·두 줄 이름에서 이름이 안 잘리는지.

### 함께 고칠 것 (같은 뿌리)

- 기획서 <b>무인 진행 규약의 “겹친 칸 겉면 = 그룹 이름만”</b> 항목을
  이번 결정으로 **갱신**해야 한다. 안 고치면 다음에 또 “규약대로”라며 되돌아간다.

**상태**: 원인 확정(결정이 뒤집힌 자리까지) · 표기 안 3개 중 **B 권함** ·
구현 계획 완료. **표기 안 결정과 고치라는 지시를 기다린다.**

## 038. [계획] 창고 우클릭 메뉴 — 삭제 추가 · 현재 분류 숨김 · 옮기기는 끌어놓기로 · 팝오버가 ✕ 를 먹는다

> **계획만 (2026-08-01). 코드는 건드리지 않았다.**

**사용자 원문 요지**
1. *"물감창고에서 물감을 오른쪽 버튼을 눌렀을 때 **삭제 버튼**이 있어야 합니다.
   삭제하면 복구 안된다고 경고를 하고 삭제해주십시오."*
2. *"저 상세창이 뜬 상황에서는 이 화면의 **엑스 버튼을 눌러도 꺼지지가 않습니다.**"*
3. *"**현재 위치가 정해져 있는데 해당 위치로 옮기기 버튼이 떠서는 안됩니다.**"*
4. *"옮기기 기능은 물감을 **드래그 앤 드롭으로 위쪽 분류에다가** 집어넣으면
   다른 곳으로 옮겨가는 것으로 하겠습니다."*

### 038-a. 삭제 메뉴가 없다

지금 우클릭 메뉴(`store_ui._move_menu`, 2026-07-31 하위 분류와 함께 만든 것)에는
‘옮기기’ 항목뿐이다. 삭제는 **물감 설정 창까지 가야** 있다 —
창고에서 물감을 보다가 지우려면 다른 창을 열어야 한다.

**계획**
- 메뉴 맨 아래에 구분선 + **삭제**. 위험한 항목이라 맨 끝, 다른 항목과 떨어뜨린다.
- 확인창에 **되돌릴 수 없음**을 분명히 적고, 함께 사라지는 것을 미리 센다:
  - 팔레트에서 쓰는 곳 개수 (`library.count_palette_refs`) — 그 블럭들도 함께 지워진다
  - 템플릿·양식은 **조각 파일(.hwp)도 지워진다**
- 꾸러미가 쓰고 있는 요소는 **막는다** — 이미 `library.MixInUse` 예외가 있으므로
  그 이름을 보여주고 지우지 않는다 (조용히 어긋나는 것보다 못 지우는 편이 낫다).
- 실제 삭제는 이미 있는 `library.delete_item()` 그대로 — 목록 저장이 먼저,
  조각 파일 삭제가 나중이라는 순서와 고아 블럭 정리가 이미 들어 있다.
- Ctrl+클릭으로 여러 개 담아 둔 상태면 **담은 것 전부**를 한 번에 (개수를 확인창에).

### 038-b. 팝오버가 떠 있으면 창의 ✕ 가 안 먹는다 — **원인 확정**

`Popover` 는 열릴 때 `grab_set()`(마우스 잡기)을 하고, 자기 자신에
`<ButtonPress-1> → _maybe_close_outside` 를 건다.

```python
def _maybe_close_outside(self, e):
    # grab 중에는 창 밖 클릭도 이 창의 이벤트로 온다 — 좌표로 구분
    if 바깥이면: self.close()
```

즉 **바깥을 누른 첫 클릭은 팝오버가 먹고 팝오버를 닫는 데 쓰인다.**
그 클릭은 ✕ 로 가지 않는다. 사용자에게는 “눌러도 안 꺼진다”로 보인다.
(제목줄 ✕ 는 창틀 영역이라 Tk 의 잡기와 얽히면 더 나빠질 수 있다 —
한 번에 안 되는지, 두 번 누르면 되는지 **실측 1건**으로 가른다.)

**계획**
- **바깥 클릭 감지를 잡기(grab) 없이** 한다: 팝오버가 열려 있는 동안만
  최상위 창에 `<ButtonPress-1>` 을 걸어 팝오버 밖이면 닫는다. 잡기가 없으면
  클릭이 원래 목적지(✕·다른 버튼)로 그대로 간다.
  포커스가 다른 앱으로 나갈 때를 위해 `<FocusOut>` 도 함께 건다.
- 그래도 첫 클릭이 소비돼야 하는 경우(메뉴를 닫기만 하고 싶을 때)와
  통과해야 하는 경우가 갈리므로, **닫히면서 통과**를 기본으로 한다 —
  메뉴를 닫으려고 누른 곳이 버튼이면 그 버튼이 눌리는 것이 자연스럽다.
- 안전망: 팝오버가 살아 있는 동안 부모 창의 `WM_DELETE_WINDOW` 가 오면
  **팝오버를 먼저 닫고** 원래 닫기를 이어서 부른다 (잡기가 남아 창이 못 닫히는 일 방지).
- 이 부품은 앱 전체가 쓰므로(팔레트 고르개·블럭 우클릭·사진 폴더 고르기 …)
  **한 곳만 고치면 전부 낫는다.** 035 의 팝오버 z 순서 문제와 같은 파일이다.

### 038-c. 지금 있는 분류로 ‘옮기기’ 가 뜬다

`_move_menu` 가 미분류를 포함한 **모든** 분류를 나열하고, 지금 분류에는 ● 만 붙인다.
화면(첨부)에서 미분류에 있는 물감인데 `미분류 로 옮기기 ●` 가 그대로 보인다 —

**계획**: 지금 분류는 **목록에서 뺀다**(● 표시도 함께 없앤다). 갈 수 있는 곳만 남는다.

### 038-d. 옮기기의 주 입구를 **끌어놓기**로

  **삭제(와 앞으로 붙을 것들)만** 남아 훨씬 단순해진다. → 이 해석으로 진행.

## 039. [삭제] 도구 ‘라이브러리’ 폐지

> **계획만 (2026-08-01, 사용자 지시: "기획에 반영해주십시오"). 코드는 건드리지 않았다.**

**사용자 원문**: *"도구에서 라이브러리 기능을 삭제해야합니다. 지금 아무 짝에도
쓸모없는 기능입니다."*

### 왜 쓸모가 없어졌나 (맞는 판단이다)

‘라이브러리’ 도구는 **물감 설정 창(LibraryManager)을 통째로 여는 버튼**이다
(`app.fn_open_library()`). 만들 당시에는 등록한 서식·문자·템플릿·양식을 보는
유일한 창이었다. 그런데 그 뒤로 **물감 창고**가 설정 창 안에 생겨 같은 일을
더 잘하게 됐다 — 분류 탭·하위 분류·미리보기·끌어놓기가 전부 창고에 있다.
게다가 022 에서 **만들기 입구를 분류별 창으로 갈라내면서** 물감 설정 창을
거칠 이유가 한 번 더 줄었다. 남은 것은 “창 하나 더 여는 버튼”뿐이다.

### 계획 — 021(‘기본 서식’ 폐지)과 **같은 절차**를 그대로 쓴다

1. `builtin_actions.BUILTIN_ACTIONS` 에서 `library` 항목을 뺀다.
2. `builtin_actions.RETIRED_KEYS` 에 `"library"` 를 더한다 →
   **이미 팔레트에 놓여 있던 블럭도 자동으로 걷힌다**
   (`palette._drop_retired_tools`, 021 때 만들어 둔 길).
3. `app.BUILTIN_DISPATCH` 에서 `"library"` 줄을 지운다.
4. `theme.BLOCK_ICON["library"]` 정리.
5. `DEFAULT_MAIN_KEYS` 에는 원래 없다 — 확인만.

### 지우면 **안 되는** 것 (같이 지우면 다른 곳이 깨진다)

`fn_open_library()` 함수와 `library_ui.open_manager()` 자체는 **남긴다.**
지금 이 길을 쓰는 곳이 더 있다:

| 쓰는 곳 | 무엇 |
|--|--|
| 도구 **특수기호** | `fn_open_library(cat="문자")` |
| 사진 폴더 관리 | `fn_open_library(cat="사진")` (도구 판의 [설정] · 사진 폴더 고르개) |
| 튜토리얼 | `open_library_char/form/photo/…` |

즉 **없애는 것은 ‘라이브러리’ 도구 블럭 하나**이고, 물감 설정 창은 다른 이름으로
계속 불린다.

### 곁가지 — 나중에 함께 볼 것

028(특수기호 분류 복원)·029(사진 폴더를 판 안에서)를 반영하고 나면
물감 설정 창을 부르는 자리가 **거의 없어진다.** 그때 그 창 자체를 어떻게 할지
(없앨지, 창고로 흡수할지) 한 번 정리할 만하다 — 이번 라운드 범위 밖.

### 검증

- 팔레트에 ‘라이브러리’ 블럭을 놓아 둔 상태에서 프로그램을 켜면 **그 칸이 사라진다**.
- 도구 목록·창고 ‘도구’ 탭에 ‘라이브러리’가 안 보인다 (7개 → 6개).
- ‘특수기호’ 도구와 사진 폴더 관리는 **그대로 동작**한다 (같은 창을 쓰지만 다른 입구).
- 021 때 만든 `RetiredToolTest` 에 `library` 케이스를 더한다.

**상태**: 계획 완료. **고치라는 지시를 기다린다** (021 과 같은 절차라 위험이 낮다).

## 040. [질문→계획] `\` 와 `\이름\` 이 다르게 취급된다 — 누르면 무엇이 일어나야 하나

> **계획만 (2026-08-01). 코드는 건드리지 않았다.**

**사용자 원문 요지**
- *"`\` 로 자리만 지정되어있는 경우랑 `\어쩌구\` 이렇게 이름으로 지정되어있는
  경우가 다르게 취급되는 경우가 많은데, 저렇게 나뉘는 경우에는 **바로 출력되는 게
  아니라 옵션을 골라야 한다**고 했던 것 같습니다. 어떻게 하면 되는 것인지?"*

### 지금 실제로 어떻게 도는가 (코드 실측)

`app._run_palette_block()` 기준:

| 물감 | 자리 모양 | 누르면 |
|--|--|--|
| 템플릿 | `\` 만 (이름 없음) | **바로 꽂는다** — 빈칸인 채로 |
| 템플릿 | `\이름\` 이 하나라도 있음 | **채우기 표가 뜬다** (`open_template_table`) |
| 양식 | 자리 수 > 0 (이름 유무 무관) | **채우기 표가 뜬다** (`open_form_table`) |
| 양식 | 자리 없음 | 그냥 새 문서로 열린다 |

템플릿의 두 줄이 사용자가 말한 “다르게 취급”이다. 근거는 코드 주석에 있다 —
*“이름을 붙였다는 것 자체가 ‘표로 채울 물건’이라는 선언이다 (2026-07-27)”*.

### 문제 — **결정이 셋인데 서로 어긋난다**

| 결정 | 내용 | 지금 |
|--|--|--|
| 2026-07-27 | 이름 있는 자리 = 자동으로 채우기 표 | **구현됨** (위 표) |
| 2026-07-31 (무인 진행 규약 · 기획서 H-5) | **왼쪽 클릭 = 빈칸인 채로 실행**,<br>**채워서 꽂기 = 우클릭 메뉴** | 우클릭 입구 **미구현** (033-b) |
| 2026-08-01 (이번 기억) | 나뉘는 경우엔 **바로 출력 말고 옵션을 고른다** | 없음 |

그래서 같은 ‘템플릿 버튼’인데 **어떤 것은 바로 꽂히고 어떤 것은 창이 뜬다.**
누르기 전에 무엇이 일어날지 알 수 없는 것이 지금의 혼란이다.

### 정할 것 — 세 안

| 안 | 왼쪽 클릭 | 채워서 꽂기 | 평가 |
|--|--|--|--|
| **A (사용자 기억)** | 빈칸이 있는 물감이면 **작은 팝오버**로 고르기:<br>`빈칸인 채로 꽂기` / `채워서 꽂기` | 그 팝오버에서 | **예측 가능**. 누르면 늘 같은 것이 뜬다.<br>대신 한 번 더 누른다 |
| B (2026-07-31 규약) | 늘 빈칸인 채로 즉시 | 우클릭 메뉴 | 빠르다. 대신 **우클릭을 배워야** 하고,<br>지금의 자동 표는 없애야 한다 |
| C (지금) | 이름 있으면 표, 없으면 즉시 | — | **예측 불가** — 이번 질문의 원인 |

**권함: A.** 이유는 하나다 — **버튼 하나가 늘 같은 행동을 해야** 손이 익는다.
지금은 물감마다 달라서 “이건 창이 뜨던가?”를 매번 떠올려야 한다.
A 로 가면 팝오버 두 줄이 늘 같은 자리에 뜨고, 아래 줄이 곧 033-b 가 말한
‘채워서 꽂기’ 입구가 된다 — **우클릭 메뉴를 따로 만들 필요도 없어진다.**

**A 를 고를 때의 잔결정**
- 빈칸이 **없는** 물감은 팝오버 없이 즉시 꽂는다 (고를 것이 없으므로).
- 팝오버 두 줄의 이름은 자리 모양을 그대로 말한다:
  `빈칸인 채로 꽂기 (\ 가 그대로 남습니다)` / `채워 넣고 꽂기 (표에서 채웁니다)`.
- 이름 있는 자리는 **표**로, 이름 없는 `\` 만이면 **순서대로 입력**으로 간다 —
  갈래는 팝오버 **뒤에** 정해지므로 사용자는 신경 쓸 필요가 없다.
- 양식도 같은 규칙으로 통일한다 (지금은 양식만 이름 유무와 무관하게 표).
- 우클릭 메뉴에는 남기지 않는다 (038-d 에서 우클릭은 **삭제 전용**으로 정리 중).

### 함께 고칠 것

- **033-b** 가 “우클릭 채워서 꽂기 미구현”으로 남아 있는데, A 를 고르면
  그 항목은 **없어진다**(팝오버가 그 일을 한다). 033-b 의 처리 방향이 A/B 선택에
  직접 걸리므로 **같은 라운드에서 함께 정해야 한다.**
- **033-a**(등록 2 · 채우기 1 불일치)와도 만난다 — 팝오버에서 ‘채워 넣고 꽂기’를
  골랐을 때 채울 수 없는 자리가 섞여 있으면 그 자리에서 알려야 한다.
- 기획서 무인 진행 규약의 **“채워서 꽂기 입구 = 우클릭 메뉴”** 줄도 함께 갱신.
