# 스크립트 블럭 + 제작용 MCP — 설계 검토

작성 2026-07-29 / 브랜치 `feature/script-mcp` / **아직 코드 없음. 결정 먼저.**

## 무엇을 하려는 것인가

지금 팔레트가 실행할 수 있는 것은 네 가지로 고정돼 있다 — 문자·템플릿·양식·서식 조합.
"한글에서 되긴 되는데 이 앱에는 그 동작이 없는" 경우(예: 쪽 번호 매기기, 표 나누기,
각주 달기, 머리말 갈아끼우기)는 지금 방법이 없다. 그래서 두 가지를 만든다.

| | 누가 쓰나 | 하는 일 |
| --- | --- | --- |
| **① 스크립트 블럭** | 일반 사용자 | 남이 만든 스크립트를 받아 팔레트에 얹고 클릭해서 실행 |
| **② 제작용 MCP** | 만드는 사람(=Claude를 붙인 사람) | 실제 한/글에 붙어 동작을 시험하고, 되는 것만 스크립트로 굳힘 |

②는 ①의 **저작 도구**다. 순서상 ①의 형식(스크립트가 무엇인가)이 먼저 정해져야
②가 무엇을 뱉을지 정해진다. 그래서 이 문서의 핵심 결정은 전부 ①에 있다.

---

## 결정 1 (가장 중요) — 스크립트는 무엇으로 쓰나

세 갈래가 있고, 되돌리기 가장 비싼 결정이다.

### 갈래 A. 선언적 JSON 스텝 목록
기존 `function` 블럭의 `actions` 배열을 확장하는 방향. `{"op":"run","action":"TableCellBorderAll"}`
같은 스텝을 나열한다.

- 장점: 안전하다. 검증할 수 있고, UI에서 스텝을 보여주고 고칠 수 있다. 기존 구조와 이음매가 없다.
- 단점: 조건·반복·계산이 없다. "표 안이면 A, 아니면 B" 같은 것이 안 된다. 결국 스텝 언어에
  if/loop를 넣게 되고, 그건 못 만든 프로그래밍 언어가 된다.

### 갈래 B. 파이썬 원본을 그대로 `exec`
- 장점: 표현력 최대. Claude가 짜기도 제일 쉽다.
- 단점: **임의 코드 실행**이다. 이 앱은 이미 라이브러리를 zip으로 주고받는 문화가 있고
  (`docs`의 내보내기/가져오기), 거기에 스크립트가 섞이면 "동료가 준 zip을 열었더니
  파일이 지워졌다"가 가능해진다. 교사끼리 주고받는 도구에서 이건 감당하기 어렵다.

### 갈래 C — **추천**: 제한된 파이썬 (화이트리스트 네임스페이스)
파이썬 문법 그대로 쓰되, 스크립트가 볼 수 있는 이름을 우리가 정한 `hwp` 파사드
하나로 묶고 `import`·`open`·`__builtins__` 를 막는다.

```python
# 스크립트 예시 (그냥 파이썬이다)
if hwp.in_table():
    hwp.run("TableCellBorderAll")
else:
    hwp.insert("표 안에서 눌러주세요")
```

- 장점: 조건·반복이 되면서, 파일/네트워크/프로세스로 나가는 길이 없다. 노출 API가
  곧 문서가 되므로 Claude가 짜기도 쉽다(MCP가 같은 목록을 그대로 보여준다).
- 단점: 완전한 샌드박스는 아니다. 파이썬에서 `exec` 탈출은 원리적으로 완전히 막지
  못한다(악의적으로 파고들면 뚫린다). **그래서 "실수·사고 방지"까지가 이 방벽의
  약속이고, "악의적 공격 방어"는 출처 표시와 설치 시 경고로 처리한다.**

> 판단: C. A는 곧 벽에 부딪히고, B는 이 앱의 배포 문화와 맞지 않는다.
> C를 택하되 **스크립트는 코드다**를 사용자에게 감추지 않는다 —
> 설치할 때 만든 사람과 원본 코드를 보여주고 한 번 확인받는다.

## 결정 2 — 되돌리기(Undo)를 어디까지 보장하나

이미 엔진에 `doc_fingerprint()` / `undo_to(mark)` 가 있다(`hwp_engine.py:551,564`).
스크립트 실행 전에 mark를 잡고, 중간에 실패하면 통째로 되돌린다.
이건 두 군데서 값을 한다.

- 사용자: 남이 만든 스크립트가 문서를 반쯤 망가뜨리고 죽는 사태를 막는다.
- 제작자(MCP): **시험 → 확인 → 되돌리기**를 반복할 수 있다. 이게 MCP의 핵심 가치다.
  "한/글에서 이 동작이 되나?"를 문서를 버리지 않고 수십 번 물어볼 수 있다.

## 결정 3 — 스크립트는 어디에 사나

`data/scripts/<id>.py` + `library.json`에 메타(이름·설명·만든이·필요 조건).
템플릿 조각(`data/fragments/*.hwp`)과 같은 취급 — 내보내기 zip에 함께 들어가고,
가져오기 때 **스크립트가 든 zip은 별도 경고**를 띄운다.

## 결정 4 — 블럭 종류를 새로 만드나

새 `type: "script"` 블럭 하나 추가. `run_block()`(`engine_library.py:1378`)에
분기 한 줄이 는다. 팔레트·라이브러리 UI는 기존 규칙(칸 수, 이름, 아이콘)을 그대로 탄다.
`builtin_actions`(앱 기능)와는 별개다 — 저건 앱이 가진 창을 여는 것이고, 이건 사용자 것이다.

## MCP 서버 설계 (②)

### 무엇인가
Claude Code에 붙는 stdio MCP 서버. **이 저장소 안에 있고**(`mcp_server/`),
`hwp_palette.hwp.hwp_engine`을 그대로 임포트해 쓴다. 즉 앱과 같은 COM 연결 방식을
쓰므로 "MCP에서 되던 게 앱에서는 안 되는" 어긋남이 생기지 않는다.

### 도구 목록 (초안)

| 도구 | 하는 일 | 왜 필요한가 |
| --- | --- | --- |
| `status` | 연결 여부, 문서 이름, 커서 위치, 표 안인지 | 시험 전 상태 확인 |
| `mark` / `rollback` | undo 지점 잡기 / 되돌리기 | 시행착오의 전제 |
| `run_action(id)` | 한/글 액션 실행 (`HAction.Run`) | 동작 탐색의 본체 |
| `set_param(set, field, value)` + `run_with_param` | ParameterSet 조작 | 값이 필요한 동작 |
| `read_selection` / `get_pos` / `doc_text_around` | 결과 관찰 | "정말 됐는지" 확인 |
| `list_actions(keyword)` | 액션 ID 검색 | 이름을 몰라서 못 하는 게 대부분 |
| `save_script(name, code)` | 스크립트로 굳혀 `data/scripts/`에 저장 | 시험의 결과물 |
| `test_script(id)` | 저장된 스크립트를 실제 실행 후 롤백 | 굳힌 뒤 재확인 |

### 작업 흐름
```
사람: "표 안 모든 셀에 세로쓰기 넣는 기능 만들어줘"
Claude → status → mark → run_action 여러 개 시도 → read로 확인 → 실패면 rollback
      → 되는 조합을 찾으면 save_script → test_script → 사람에게 보고
사람: 팔레트에 그 스크립트 블럭을 얹는다
```

### 경계
- MCP는 **사용자의 진짜 한/글 문서를 건드린다.** 빈 문서에서 시험하도록 강제할지
  (열린 문서가 저장되지 않았으면 거부) 정해야 한다 → 초안은 **경고 후 진행**,
  `mark`를 반드시 먼저 잡게 한다.
- MCP는 개발자 도구다. 일반 사용자 배포본(exe)에는 넣지 않는다.
