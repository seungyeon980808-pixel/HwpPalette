## ① 시각적 '한 줄'을 잡을 수 있는가 → 된다

아래 액션이 전부 `True` 로 동작한다.

```
MoveLineBegin  MoveLineEnd  MoveLineUp  MoveLineDown
MoveSelLineBegin  MoveSelLineEnd
MoveParaBegin  MoveParaEnd  MoveSelParaEnd
MoveNextWord  MovePrevWord  MoveSelNextWord  MoveSelPrevWord
```

**한 줄을 얻는 관용구** (스파이크의 `scan_lines()`):

```
SetPos(0, para, 0)
반복:
    MoveLineBegin      → GetPos = 줄 시작
    MoveSelLineEnd     → GetTextFile("TEXT","saveblock") = 그 줄의 글자
    Cancel
    MoveLineEnd        → GetPos = 줄 끝,  KeyIndicator()[6] = 줄이 쓴 폭(칸)
    MoveRight          → 다음 줄 첫 글자 (문단이 바뀌면 종료)
```

실측 예 (문단0):

```
줄0: pos 16~65 (49자) 끝칸=87 | 우리 학교 과학실에서는 … 관찰 결과를
줄1: pos 65~102 (37자) 끝칸=63 | 기록하는 활동을 진행하는데, … 지켜야 한다.
```

**함정 두 가지**

- **문단 첫 글자의 pos 가 항상 0 이 아니다.** 문서 첫 문단은 `MoveDocBegin` 직후
  `GetPos() = (0, 0, 16)` 이다(앞의 16칸은 구역 정의 등 보이지 않는 컨트롤).
  다른 문단은 0 에서 시작한다. **줄 시작 위치를 0 으로 가정하지 말고 반드시
  `MoveLineBegin` + `GetPos` 로 얻을 것.** (MEMORY 의 "빈 탭에서도 (0,0,16)" 과 같은 뿌리)
- 마지막 줄에서 `MoveRight` 는 다음 문단으로 넘어간다. 문단 번호로 종료 판정해야 한다.

## ② 남는 폭 — 직접 재는 API 는 없다

없는 것(이름을 대면 `AttributeError`): `GetCaretPos`, `CaretPos`, `GetCursorPos`,
`PositionToRect`, `GetPosRect`, `HwpUnitToPoint`.
`GetPosBySet()` 이 주는 것도 `List` / `Para` / `Pos` 세 개뿐 — **좌표는 없다.**

쓸 수 있는 유일한 폭 대용치는 **`KeyIndicator()` 의 7번째 값(index 6) = 칸 번호**다.
한글 한 글자 = 2칸, 공백·영숫자 = 1칸. 실측으로 자리를 확정했다
(index 5 = 줄 번호, index 6 = 칸 번호, 둘 다 1부터).

### 함정: 양쪽 정렬이 남는 폭을 감춘다

한글 기본 정렬은 양쪽 정렬(`HParaShape.AlignType = 0`)이고, 이때 한글이
**어절 간격을 늘려 줄 끝을 여백에 딱 맞춘다.** 그래서 끝칸은 어느 줄이나 늘 꽉 찬 값이다.

같은 문단을 정렬만 바꿔 가며 잰 값:

```
AlignType=0 (양쪽) : 끝칸 = [87, 86, 86, 86, 86, 17]
AlignType=1 (왼쪽) : 끝칸 = [87, 86, 85, 85, 85, 17]
AlignType=2 (오른쪽): 끝칸 = [87, 86, 86, 86, 86, 86]
```

→ **끝칸을 그대로 읽으면 "모든 줄이 꽉 찼다"는 잘못된 답이 나온다.**
진짜 남는 폭을 재려면 정렬을 잠깐 왼쪽으로 바꿨다가 되돌려야 한다
(스파이크의 `slack_by_left_align()`). 어절 단위를 켠 상태의 실제 남는 폭은
`[0, 7, 4, 5, 2]` 칸 — 즉 **최대 3.5 한글 글자분**이 비어 있었다.

### 대안(해 보고 되돌리기)도 실용적이다

자간을 걸고 줄 경계를 다시 읽는 데 걸리는 시간:

| 동작 | 1회 비용 |
|--|--|
| `GetPos()` | 0.2ms |
| `KeyIndicator()` | 0.2ms |
| `MoveLineEnd` (액션) | 8.8ms |
| 문단 하나 줄 전체 훑기 | 51ms |

문단 하나(6줄)를 위→아래로 훑으며 자간을 거는 예행이 **2.0~4.1초**. 선택 영역
한두 문단이면 충분히 빠르고, 문서 전체(수십 문단)면 진행 표시가 필요한 수준이다.

## ③ 자간을 선택 영역에만 걸고 되돌리기 → 된다

**필드 이름 주의.** `HCharShape.Spacing` 은 **없다**. 글자 종류마다 따로다:

```
SpacingHangul  SpacingLatin  SpacingHanja
SpacingJapanese  SpacingOther  SpacingSymbol  SpacingUser
```

한글만 바꾸면 줄에 섞인 영문·숫자·기호가 안 따라오므로 **일곱 개를 모두 같은 값으로**
설정해야 한다. 값의 단위는 **퍼센트 정수**(−6 = 자간 −6%). 되읽기도 같은 필드로 된다.

```python
select_range(hwp, para, start, end)          # SelectText(para,start,para,end) 로 한 번에
act.GetDefault("CharShape", ps.HCharShape.HSet)   # ← 현재 서식을 먼저 불러올 것
for f in SPACING_FIELDS: setattr(ps.HCharShape, f, pct)
act.Execute("CharShape", ps.HCharShape.HSet)
```

`GetDefault` 를 생략하면 글꼴·크기까지 기본값으로 덮어써 문서가 망가진다
(앱의 `set_char_shape()` 와 같은 관례).

실측 결과:

- 건 자리 자간 = −6, 바로 다음 줄(범위 밖) 자간 = 0 → **범위가 정확히 지켜진다.**
- 자간 0 을 다시 걸면 줄 경계가 **원래 값과 완전히 일치**하게 복구된다.
- `Undo` **한 번**으로도 원래 자간으로 돌아온다 → **자간 적용 1회 = 되돌리기 1칸.**
  줄마다 여러 번 시도하면 되돌리기 칸이 그만큼 쌓이므로, 016 의 위험요소 4
  (↺ 되돌리기 묶음 세기 편입)는 **반드시** 지켜야 한다.
- `SelectText(para, start, para, end)` 가 동작한다 → 글자 수만큼 `MoveSelRight` 를
  반복할 필요 없음(느린 액션 호출을 수십 번 아낀다).

## ④ 재흐름 범위 → 손댄 문단 안에 갇힌다

문단1 **전체**에 자간 −8% 를 걸고 다섯 문단을 모두 다시 잰 결과:

```
       전                          후
문단0  줄수2 줄시작[16,65]        줄수2 줄시작[16,65]     변화 없음
문단1  줄수2 줄시작[0,47]         줄수2 줄시작[0,51]      ← 이 문단 안에서만 다시 흐름
문단2  줄수2 줄시작[0,50]         줄수2 줄시작[0,50]      변화 없음
문단3  줄수1 줄시작[0]            줄수1 줄시작[0]         변화 없음
문단4  줄수6 줄시작[0,49,…,244]   줄수6 줄시작[0,49,…,244] 변화 없음
```

**문단 경계를 넘는 재흐름은 없다.** 줄 수가 바뀌면 아래 문단의 *문서상 줄 번호·페이지*는
밀리지만, 문단 안의 줄 구성(어느 글자가 어느 줄에 있는지)은 그대로다.
우리는 위치를 `(문단, pos)` 로 다루므로 아래쪽을 다시 계산할 필요가 없다.

→ **위에서 아래로 한 번 훑기로 충분하다.** (016 의 "위→아래 순서가 옳다"는 판단은 맞았고,
근거는 예상보다 강하다 — 아래를 다시 볼 필요조차 없다.)

## ⑤ 예상 밖의 발견 — 한글 기본 줄나눔은 '글자 단위'다

016 의 전제는 "한글에 이미 어절 단위 줄바꿈이 있고, 켜면 줄이 헐렁해진다"였다.
**새 문서의 기본값은 어절 단위가 아니다.** `HParaShape.BreakNonLatinWord` 의 기본값이
`1`(글자 단위)이라 **지금도 단어 중간에서 잘리고 있다.**

같은 문단을 두 값으로 재본 실측:

```
BreakNonLatinWord = 0 (어절 단위)        BreakNonLatinWord = 1 (글자 단위, 기본값)
 줄0 …대 도시가 침수될                     줄0 …대 도시가 침수될
 줄1 … 필요하다. 특히                      줄1 …하다. 특히 이산화   ← 단어 중간에서 잘림
 줄2 …방출되는 적외선을                    줄2 … 적외선을 흡수하였  ← 잘림
 줄3 … 끌어올리는 데에                     줄3 … 데에 결정적인 역   ← 잘림
 줄4 …에 걸쳐 되돌리기                     줄4 …돌리기 어려운 변화  ← 잘림
 남는 칸 [0, 7, 4, 5, 2]                  남는 칸 [0, 1, 2, 2, 2]
```

의미:

- 사용자가 말한 "단어가 줄 끝에서 잘린다"는 **실제로 일어나는 현상**이고, 원인은
  자간이 아니라 **줄나눔 기준**이다.
- 방식 A 는 그래서 **두 단계**가 된다: ⓐ `BreakNonLatinWord = 0` 으로 어절 단위를 켠다
  → ⓑ 그 결과 생긴 남는 폭(최대 7칸 관측)을 자간을 좁혀 메운다.
- ⓐ만 해도 사용자의 1차 불만("단어가 잘린다")은 해결된다. ⓑ는 "줄이 헐렁하다"를 다듬는 것.
  **단추를 굳이 나눌 필요는 없지만, ⓐ가 본체이고 ⓑ가 마감이라는 점은 설명에 반영할 것.**
- 다만 `BreakNonLatinWord` 도 문단 모양이라 **문단 단위로만** 걸린다. 줄 단위가 아니다.

## ⑥ 필요한 자간을 계산으로 맞힐 수 있다 (더듬어 찾기 불필요)

자간 p% 를 걸면 글자마다 폭이 p% 줄므로, 줄에 n 글자가 있으면
**새로 들어오는 글자 수 ≒ n/(1+p/100) − n** 이다. 47자짜리 줄로 실측:

| 자간 | 실측 | 이론 |
|--|--|--|
| −2% | +2자 | +1.0자 |
| −4% | +2자 | +2.0자 |
| −6% | +3자 | +3.0자 |
| −8% | +4자 | +4.1자 |
| +2% | −1자 | −0.9자 |
| +4% | −2자 | −1.8자 |

**±1자 안에서 맞는다.** (어긋나는 만큼은 어절 경계 때문에 생기는 반올림이다.)
→ 필요한 자간을 먼저 계산해 **한 번에 걸고, 안 되면 한 단계만 더** 시도하면 된다.
−2/−4/−6/−8 을 차례로 더듬을 필요가 없어 문단당 COM 호출이 절반 이하로 준다.

## 방식 A 구현 설계 (실측에 근거한 것만)

```
전제: 대상은 선택 영역(없으면 커서 문단). 표 안(GetPos()[0] != 0)은 1차 범위에서 제외.

1. 대상 문단 목록을 만든다.
2. 문단마다:
   a. BreakNonLatinWord = 0 (어절 단위)  ← 잘림을 없애는 본체
   b. 원래 AlignType 을 기억하고 1(왼쪽)로 바꾼다  ← 남는 폭을 드러내기 위해
   c. scan_lines() 로 줄별 (시작pos, 끝pos, 끝칸) 을 얻는다
   d. 기준 폭 = 그 문단에서 관측된 최대 끝칸
   e. 위에서 아래로, 마지막 줄을 뺀 각 줄에 대해:
        필요칸 = (다음 줄 첫 어절의 칸 폭) − (기준폭 − 그 줄 끝칸)
        필요칸 <= 0 이면 건드리지 않는다
        p = -ceil(필요칸 * 100 / (2 * 그 줄 글자수))
        p < 자간 하한이면 **그 줄은 그냥 둔다** (무리하지 않기)
        아니면 그 줄 범위에 자간 p 를 걸고, 줄 끝 pos 가 늘었는지 한 번만 확인
        늘지 않았으면 p 를 한 단계(2%) 더 좁혀 **딱 한 번만** 재시도, 그래도 안 되면 원복
   f. AlignType 을 원래대로 되돌린다
3. 전체를 되돌리기 한 묶음으로 봉인한다 (record_undo_point / seal_undo_point).
```

### 진동(늘림/줄임 반복) 방지 — 실측에 비춘 조정

016 이 걱정한 무한 루프는 **방식 A 에서는 구조적으로 생기지 않는다.** 근거:

- 재흐름이 문단 밖으로 안 나가고(④), 위→아래로 한 번만 지나가며 이미 지난 줄을
  다시 보지 않기 때문이다.
- 그래도 **한 줄당 자간 적용은 최대 2회**로 못 박는다(계산 1회 + 보정 1회).
  ⑥의 예측이 ±1자 안에서 맞으므로 2회면 충분하다.
- **좁히기만 한다.** 넓히기(+)를 섞으면 앞 줄이 다시 흔들려 진동의 여지가 생긴다.
  넓히기는 방식 B 로 올릴 때 다시 검토한다.
- 한 줄에 자간이 이미 0 이 아닌 곳이 섞여 있으면(사용자가 손으로 준 서식)
  **그 줄은 건너뛴다.** 남의 서식을 덮어쓰지 않는다.

### 자간 한도 — 016 제안(−8%~+4%) 재검토

- **하한 −8% 는 적절하다.** 실측에서 −8% 는 47자 줄에 4자를 더 넣는 힘이고,
  이는 한국어 어절 하나(평균 3~4자)를 당겨 올리기에 딱 맞는 크기다.
  더 좁히면 글자가 붙어 보이기 시작한다.
- **실제로는 대부분 −2%~−4% 로 끝난다.** 어절 단위를 켠 뒤 관측된 남는 폭이
  최대 7칸(3.5자)이었고, 6줄짜리 문단 예행에서 −4%가 최댓값, 나머지는 −2%였다.
- **상한 +4% 는 방식 A 에서 필요 없으므로 뺀다.** 넓히기를 쓰지 않기 때문이다.
  방식 B 로 올릴 때 되살린다.
- 권장 확정값: **−8% ~ 0%, 2% 단위.** 한도 안에서 안 되는 줄은 손대지 않는다.

### 남은 위험 / 1차 범위에서 뺄 것

- **한 줄에 서식이 여러 벌**(016 위험 2): 위처럼 "이미 자간이 0이 아니면 건너뛰기"로 피한다.
- **정렬을 잠깐 왼쪽으로 바꾸는 것**이 유일하게 마음에 걸리는 부분이다. 문단모양 변경이
  되돌리기 칸을 더 쓰고, 중간에 예외가 나면 정렬이 왼쪽인 채로 남을 수 있다.
  → 반드시 `try/finally` 로 되돌리고, 되돌리기 봉인 안에 넣는다.
  → 대안: 정렬을 안 건드리고 "자간을 걸어 보고 줄 끝 pos 가 늘었는지"만 보는 방식도
    실측상 동작한다(②의 (다)). 더 안전한 대신 시도 횟수가 는다.
    **1차는 안전한 쪽(정렬을 안 건드리는 쪽)으로 가고, 느리면 그때 정렬 측정을 얹는다.**
- **표 안**: 셀마다 폭이 달라 기준 폭 계산이 달라진다. 1차 제외.
- **각주·머리말**: `GetPos()[0] != 0` 로 함께 걸러진다.
